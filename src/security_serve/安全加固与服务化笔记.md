## G0 五层重构：先立结构，再长防线

> 记忆钩子：**只搬结构不添功能；一处注册两产出；冻结旧版当标尺。**

### 1. 决策：先重构再加固

- 旧版 `src/my_agent/agent.py` 827 行单文件：工具实现、两份手工 schema 清单（TOOL_FUNCTIONS 与 TOOLS）、主循环、会话/压缩、记忆混居一体；在其上继续叠防线，边界只会更糊。
- 决策：在 G 阶段目录先重构（结构变、行为一字不变），防线在清晰边界上逐层长出；旧版**冻结不动**，作为对照基线（evals/eval.py 仍 import 旧版，零风险）。

### 2. 五层划分与单向依赖

| 层 | 职责 | 依赖 |
|---|---|---|
| config | 全部调参集中：模型接法、工具边界常量、循环/压缩阈值、数据目录、system prompt | — |
| tools | 注册表 + 9 个工具实现 | config、safety |
| safety | G 防线专属层（G0 立占位，G1-G3 逐层填肉） | config |
| memory | 会话落盘/恢复/清空、长期记忆注入、上下文统计与压缩 | config |
| loop | agent 内循环：流式决策 → 工具并行执行 → 结果回传 | config、tools |
| cli | 入口层：组装五层、跑用户对话外循环 | config、memory、loop |

- 依赖**单向无环**：cli → loop → tools → config；行为参数改一处（config），全层生效。
- safety 的接入点在 G0 就预留好：loop 的工具执行点 + tools 的实现处——防线是"插进既有缝"，不是"改写既有层"。

### 3. 注册表模式：一处注册两产出

- `TOOL_REGISTRY` 一处定义；`@tool` 装饰器工厂在 **import 时刻**同时写入 `func` 与 `schema`；文件末尾的 `TOOL_FUNCTIONS` / `TOOLS` 是两个快照视图（给执行器按名取函数 / 给 LLM API 挂报文）。
- 价值：消除旧版两处手工清单的漂移风险；加新工具只改一处（写实现 + 挂装饰器）。
- 机制三层：`tool(...)` 返回闭包 deco（四个参数装进 cell）；`deco(fn)` 写注册表并**原样返回 fn**；`@` 语法糖 = 链式调用 `tool(args)(fn)`。装饰器不改函数，只借 def 语句的执行时机干私活——注册写入发生在 import，9 个工具的捕获互不串台（每次 `tool()` 调用产生独立 cell）。

### 4. 行为不变的验收：step0 对照

- 重构类任务的验收标准 = **行为不变**，对照物必须冻结：工具名集合、schema 逐字（按名排序后 json 比对，消除 dict 顺序差异）、12 项确定性工具输出——22 项全 PASS。
- 联网工具（web_search / web_fetch）依赖外部网络，不进自动对照，留 CLI 冒烟覆盖——验收物按确定性边界切分。

### 5. 导入写法与包形态

- 包内统一**完整名绝对导入**；editable install 挂整个 src/，直跑与被导入两种方式都成立；`agent/` 是 regular package（`__init__.py` 立包身份），`security_serve/` 层是 namespace（纯目录分层，现状够用）。
- 完整推理见同目录 `python_import笔记.md`（身份 / sys.path / 写法契约 / 报错速查），此处不重复。

## G1 路径白名单：文件系统工具的闸门

> 记忆钩子：**规范化让逃逸现形，分隔符封死同级；可控出口同过一闸，区内行为零改动。**

### 1. 威胁模型与方案

- read_file / list_dir / grep 的路径参数完全由 LLM（或注入文本）可控——没有闸门时可以读盘上任意文件。
- 方案：白名单闸门。路径规范化后落在 `ALLOWED_ROOTS`（当前 = 仓库根，由 config.py 位置上推三级，与启动目录无关）内才放行，区外一律拒绝。
- 覆盖判定：**路径参数可控的工具出口都要过同一道闸**——三个文件工具全上；search_knowledge / remember 的路径是内部写死的常量，天然无此暴露面。

### 2. check_path 两步核心

| 步骤 | 操作 | 产出与作用 |
|---|---|---|
| ① 规范化 | `os.path.realpath(path)` | 相对→绝对、消解 `..` 与符号链接；消化后仍在区内就放行，逃出区外才拒 |
| ② 目录级前缀判断 | `target == base or target.startswith(base + os.sep)` | `==` 管根本身，`startswith(根+分隔符)` 管内部 |

三个精度点：

- **补 os.sep**：裸 startswith 会被同级目录骗过（`my-ai-app-evil` 确实以 `my-ai-app` 开头）；补上分隔符 = 强制要求"根目录之后紧跟目录边界"。
- **normcase 两侧**：Windows 不区分大小写，`e:\WORKSPACE\...` 与小写 base 作为字符串并不相等——normcase 统一后比对才成立。
- **两个分支的分工**：`==` 覆盖根目录自身（它结尾没有 `\`，右半够不着）；`or` 左边命中即短路。

### 3. 分隔符与大小写：一个方言包的保证

- `os.path` 是**平台别名模块**：Windows 上就是 ntpath。`realpath` / `normcase` / `os.sep` 同源配套，产物必然同一方言（Windows 全反斜杠，POSIX 全正斜杠）——统一写 `os.path.xxx` + `os.sep`，跨平台比对自然成立。
- 分工：**realpath 管"这个路径真实是什么"**（结构解析：绝对化、消 `..`、解链接、分隔符归一），**normcase 管"两个字符串在文件系统眼里是否同写法"**（小写 + 分隔符统一；产物只用于比对，不用于真实访问）。
- 三兄弟记忆：normpath 只动字符串；abspath 加绝对化；realpath 再加解链接——安全校验用最全的 realpath。

### 4. 闸门位置不变量：赶在第一次碰盘之前

- 判据是"**首次文件系统访问之前**"，不是"函数第一行"：read_file / list_dir 第一行就 getsize / isdir，闸门置顶；grep 先 `re.compile`（纯字符串计算，不碰盘），闸门在 `os.walk` 之前。
- 附带红利：正则先判使"非法正则 + 任意路径"统一返回正则错误，探测者拿不到路径区分信号（合法正则时区分仍在，属无害次序而非设计防线）。

### 5. 提示词层 + 工具层双层协作

- 实测（CLI 冒烟）：system prompt 写明边界后，LLM 对越界请求**未调工具直接拒绝**——提示词层先起作用；工具层闸门是它失效时的兜底（step1 用例 [3] 实调返回错误串）。
- 拒绝用**错误串**返回（与工具既有错误风格一致），循环不被异常打断；错误消息本身教会 LLM 边界在哪。
- 权衡记录：read_file 的 schema 描述本轮未改（改动会破坏 step0 的 schema 逐字比对）；边界告知落在 system prompt 禁止区 + cli 欢迎语示例（`E:/test/a.txt` → `pyproject.toml`，示例与能力一致）。

### 6. 攻击变体与已知边界

攻击变体 → 拦截机制映射（独立对抗验证未发现绕过）：

| 输入 | 结果 | 拦截/放行靠哪步 |
|---|---|---|
| `src\..\..\..\Windows\win.ini` | 拒绝 | realpath 消解后落区外 |
| `..\..\README.md` | 拒绝 | 同上 |
| `E:/.../README.md`（正斜杠） | 放行 | realpath 归一分隔符 |
| `e:\WORKSPACE\...\README.md`（大小写混淆） | 放行 | normcase |
| `\\localhost\c$\Windows\win.ini`（UNC） | 拒绝 | realpath 落区外 |
| `my-ai-app-evil\secret.txt`（同级前缀） | 拒绝 | os.sep 目录边界 |
| `README.md/../../pyproject.toml`（区内起点逃逸） | 拒绝 | realpath |
| 空串 | 放行（=cwd） | realpath("") → cwd，cwd 在区内即合法（记录在案） |

已知边界（方案固有属性，非缺陷）：

- `.git\config` 等区内敏感文件仍可读——白名单是目录级，区内行为刻意保持与 G0 逐字一致。
- 盘根（`E:\`）作白名单根时 `base + os.sep` 会成双分隔符——届时拼前缀前先 `rstrip(os.sep)`；当前 ALLOWED_ROOTS 是普通目录路径，不触发。

### 7. 实现决策记录

- 返回 `(bool, str)` tuple：字段少、调用点近，按位置解包最省；类型标注 `tuple[bool, str]` 就是调用方的顺序契约。字段增长时升级 NamedTuple（按名解构，相当于 JS 返回对象在 Python 的对应物）。
- 闸门只决定放不放：不放行返回错误串；放行后原逻辑一行不动——step0 回归 22 点全绿即为佐证。

## G2 ast 白名单求值器：calculate 告别裸 eval

> 记忆钩子：**白名单即解释器能力集；空 builtins 挡名字，挡不住属性链；指数先算后比上限。**

### 1. 威胁模型与方案

- 旧 `eval(expression, {"__builtins__": {}})` 并不安全：空 builtins 只挡**名字查找**，挡不住**属性访问**——实测 `().__class__.__bases__[0].__subclasses__()` 真的执行并返回全部已加载类（step2 实锤展示），是继续通向 os 等危险模块的起点；且出错报 NameError（"名字没定义"），误导排查方向。
- 方案：safety.safe_eval —— `ast.parse(mode="eval")` 解析 + 递归解释器求值，**全程无 eval**。

### 2. 白名单即解释器能力集

| 节点 | 放行范围 | 拒绝消息 |
|---|---|---|
| Constant | 仅 int/float（str/bool/None/复数一律拒） | 包含不允许的语法（str 常量） |
| BinOp | 七种算术（_BIN_OPS 查表：+ - * / // % **） | 包含不允许的语法（节点名） |
| UnaryOp | UAdd / USub（正负号） | 同上 |

- 设计姿态：不是"检查完再 eval"，而是**解释器能算什么输入就允许什么**——白名单与能力是同一个东西，Call / Attribute / Name / Lambda / Subscript / IfExp / JoinedStr / Tuple 在求值这一步就进不来。
- 求值器抛 ValueError 作统一拒绝信号，safe_eval 把它转成原因串；ZeroDivisionError / OverflowError 转算术错误串，RecursionError 转"表达式嵌套过深"。

### 3. 幂指数守卫

- `9**9**9` 会算数亿位大数挂死工具——守卫**先算出指数再比上限**（CALC_MAX_POW_EXPONENT = 10_000，config 防线常量），炸弹开算前拦下；嵌套炸弹在每层递归处被同一守卫切断。
- 边界实测：`2**10000`（恰在上限内，3011 位）放行不卡；`2**10001` 拒。
- 残留边界：数值资源消耗只有指数守卫一道（大数乘法无上限），通用资源上限归 G3 的预算/熔断主题。

### 4. 行为对齐的坑（验证代理抓到的真实缺陷）

- 内置 eval 接受前导空白，`ast.parse` 把前导空白当缩进报 SyntaxError——`' 25 + 5 '` 旧返回 `'30'`、新误拒。修复：解析前 `expression.strip()` 对齐行为（根因写进注释，探针固化进 step2 第 7 例防回归）。
- 经验：换解析器时"逐字对齐旧行为"要靠对抗探针验证，不能只测自己想到的用例。

### 5. G0 回归的处理：有意变更的标注法

- `calculate('__import__')` 的拒绝语义正是 G2 要改的——step0 该项跨版对照改为"跳过 + 说明"标注，其余 21 项照旧全绿。
- 方法论：回归不是永远全绿；**有意变更要显式标注，并给新行为指定新验收物**（此处的 step2）。

### 6. 拒绝面与浮点行为边界

- 白名单天然拒绝的语法面：Call / Attribute / Name / Lambda / Subscript / IfExp / JoinedStr / Tuple 等节点在求值步进不来——注入链（含前导空格变体）与属性逃逸同被拒。
- 深嵌套与超长输入有底：深括号嵌套干净拒绝，超长加法链触发 RecursionError 被接住不挂死。
- `strip` 只剥空白，不构成绕过面；千位大数常量放行（常量层无上限，资源风险归 G3）。
- 浮点行为与旧 eval 逐字一致：`0.1+0.2` 同为 `0.30000000000000004`，`2**(1e999-1e999)` 同为 nan——属算术而非绕过。

## G3 permission gate + 成本预算熔断：危险动作要点头，会话成本有熔断

> 记忆钩子：**默认拒绝——没说可以就不行；gate 在执行点不在工具层；MAX_STEPS 管单轮，Budget 管全会话。**

### 1. 威胁模型与方案

- 注入文本（G4 主题）或模型误判可驱动工具做危险动作：read_file 把文件内容送给模型（数据外泄出口）、remember 写持久记忆（可被注入投毒）、web_fetch 把 URL 打到外网（SSRF/外呼面）。
- 方案三件：CONFIRM_TOOLS 确认清单（config）→ 执行前人工确认 ask_user（safety，默认拒绝）→ 会话 token 预算熔断 Budget（safety）。
- 清单判据是**副作用 / 外泄面**；grep/list_dir 只读且不外送，刻意不在清单——清单本身是策略决策，放宽收紧只改 config 一处。

### 2. 默认拒绝：ask_user 的放行面

- 放行条件严格为 `strip().lower() == 'y'`：误回车、自动化脚本、stdin 关闭（EOFError）全部落到拒绝一侧——"没说可以就不行"。
- EOFError→拒绝为 G5 服务化预留：HTTP 服务没有交互终端，没人能点头 = 没人同意，远端请求不会被静默放行。
- `threading.Lock` 串行化：工具是线程池并行执行的，确认提问本质是 UI 操作必须串行——锁保证多个工具同时要确认时 input 提示逐个排队。

### 3. gate 位置不变量：执行点而非工具层

- gate 插在 loop.run_one_tool 的执行点（未知工具检查后、`func(**args)` 前），**不在 tools 层**——直接调用工具函数（step0/1/2 的对照方式）完全不受影响，step0 21 项照旧全绿就是分层价值的实证。
- 拒绝以工具结果串 `"用户拒绝执行此工具"` 回传：不走异常（循环不断）、LLM 看得到原因（下一轮自行调整）；CLI 实测 LLM 如实转述"操作被拒绝了"。
- gate 顺序在 JSON 解析与未知工具检查之后——解析失败的 call 不弹确认框。

### 4. 成本双闸：MAX_STEPS vs Budget

| 闸 | 管什么 | 计量单位 |
|---|---|---|
| MAX_STEPS | 单次提问的 LLM 轮数（防反复调工具停不下来） | 轮 |
| Budget | 整个会话累计成本（cli 进程一个账本，clear 不清零——熔断管的是真金白银） | tokens |

- 查线在每轮 LLM 调用**之前**（请求发出去就要花钱，超线不再发）；记账在调用成功**之后**（API 出错 break 的路径不计费）。
- 记账公式：输入 = context_stats_size(messages)（append 本轮产物之前量，正好就是发送出去的请求体）+ 输出 = len(final_content) + 工具调用参数字符。

### 5. 估算版取舍：字符折算 token

- 不用 API 真 usage：流式响应拿 usage 要额外开关且部分第三方服务不给，估算护栏不追求精确。
- CHARS_PER_TOKEN = 2 是折中：英文场景多记（早熔断）、中文场景少记（晚熔断），熔断线本身留余量。
- 整除取整（record(1)→0 token）；exceeded 是 `>=` 语义（恰好达线即熔断）。

### 6. 测试要点

- 放行面按枚举测：`y`/`Y`/`"Y "`/`" y"`/`"Y\t"` 放行（strip+lower 后均为 y）；回车 / EOF / yes / yy / 空串全拒——默认拒绝的语义由放行面的窄定义反推。
- from-import 是名字绑定：monkeypatch 要 patch `loop.ask_user` 才能拦到 gate，patch `safety.ask_user` 拦不到——Python 导入语义的直接应用，写测试易踩。
- 并发确认测法：多线程同时要确认，锁保证提问串行不乱码；EOF 线程全部默认拒绝；JSON 解析失败的 call 不弹确认框（gate 排在解析与未知工具检查之后）。

## G4 提示词注入防御：不可信文本圈进数据边界

> 记忆钩子：**资料是资料、指令是指令；nonce 随机，伪造出不了圈；封装是缓解，硬防线兜底。**

### 1. 威胁模型与方案

- 知识库资料、网页正文、文件内容最终都进入 LLM 上下文——都是不可信文本。攻击者在文档里藏"给 AI 的系统指令"（驱动 remember 写投毒记忆、读敏感文件、忽略规则），模型可能当真执行；remember 投毒还会在下次会话注入 system prompt 形成**持久化后门**（G3 把 remember 列入确认清单正是为这一刻埋的线）。
- 方案双层：**封装层**（loop 回传 tool 消息前统一包 wrap_untrusted 数据边界）+ **声明层**（system prompt「不可信内容边界」段教会模型把标记内文本当资料读）。
- 纵深防御：就算注入成功驱动了工具，G1 路径白名单 / G2 ast 求值器 / G3 确认闸门逐层兜底——提示词层是缓解（mitigation）不是硬防线。

### 2. 随机 nonce：提前闭合攻击的克星

- 攻击者会伪造闭合标签（`</DATA_xxx>`、`[数据结束]`、"资料结束，以下恢复系统指令"）想让数据区提前结束、把注入文本升级为"真指令"。
- nonce 每次 `secrets.token_hex(8)` 随机生成（64 bit 熵，猜中概率 1/2^64），只有匹配本次 nonce 的闭合标签才有效——伪造与**重放**（把旧封装结果整体塞进新载荷）全部失效。
- 协议收敛为唯一边界对 `<DATA_nonce>...</DATA_nonce>`：早期设计有外层固定文字标记（[资料开始/结束]），意识到固定格式可被原样伪造后砍掉——伪造面只剩"猜 nonce"一条路。
- 资料原文一字不改：封装只加包装（10 万字符/空串/unicode/转义字符边界探针实证）。

### 3. 统一封装：信任不靠枚举来源

- 所有工具结果一律封装（含错误串）——错误串虽是程序自己生成的，但"按来源区分信任"会随工具增多而漏判；loop 一处统一封装，永远不漏。
- 封装在 loop 回传 messages 处（与 G3 gate 同一个执行点理念）：run_one_tool 返回值、直接调工具函数（step0/1/2 方式）都不受影响。

### 4. 真机实测的诚实结论

- deepseek-v4-flash 对直白注入（自称"管理员频道系统指令"）**裸载荷就能识破并主动举报**——现代模型的 RLHF 对齐本身是一道天然防线。
- 封装层的价值不在直白样本的单轮对比，而在：协议化边界（判断依据从模型猜测变成明确规则）、防隐蔽注入（不自称指令、藏在正常内容里的间接注入）、弱模型/换模型不退化。
- CLI 冒烟：模型读藏毒文件后正常转述政策、明确说"资料中出现可疑内容，没有执行"——system prompt 新增的"如实告知可疑内容"条款被真实执行；session.json 中 tool 消息确认带 DATA 边界。

### 5. 封装不变量

- 四种工具结果形态（正常输出 / 未知工具错误 / 非法 JSON / G2 拒绝串）全部带 DATA 边界——统一封装点的价值：加新工具不会漏封。assistant / user 消息不封装（它们不是外部资料）；绕过 loop 直接调工具函数（step0/1/2 方式）无边界——封装与 gate 同在 loop 执行点。
- 对抗面：nonce 每次必不同；伪造闭合 + 整体重放全部失效；真闭合全文恰好一对（开始 + 结束各一）；空串 / 超长文本 / unicode 原文零改动。

## G5 FastAPI 服务化：会话从进程单例到请求级资源

> 记忆钩子：**会话跟着请求走，输出去向看 echo；服务没有终端，默认拒绝自动生效。**

### 1. 服务化的本质

- CLI 是「一个终端 + 一个用户 + 一次对话循环」，服务是「N 个并发请求各带自己的会话」——服务化不是套 HTTP 壳，是把**会话状态从进程级单例变成请求级资源**。
- 形态：POST /chat `{message, session_id}` → `{reply, session_id, used_tokens}`；GET /health。每会话独立 messages（上下文）+ 独立 Budget（成本账本）——G3 的 Budget 从「CLI 进程一个」升级为「每会话一个」。
- 会话存进程内存 dict：重启即失、多副本不共享——生产换 Redis（TTL 管时效、副本间共享），接口形态（按 session_id 存取）为迁移留好了位置。

### 2. echo 开关：逻辑一份，输出去向两种

- run_agent_turn 加 `echo` 参数并**返回 final_content**——CLI（echo=True）print 到 stdout 给终端用户，服务（echo=False）转 logging、回答从返回值拿。
- 为什么不拆两个函数：核心逻辑（流式、工具分片组装、熔断记账）是同一套，拆开就是复制粘贴漂移风险；CLI 调用处一行不改（默认值 True）。
- `_emit` 辅助：错误/熔断/超步数走 log.warning，工具调用走 log.info；流式逐字打印在 echo=False 时跳过但内容照常收集。
- `final_content = ""` 函数级初始化：首轮就熔断/超步数时 break 出来也有值可返（Budget(0) 返回空串无 NameError）。
- 返回值契约由循环结构保证：break 的唯一正常出口是「本轮无工具调用」的纯文字轮——能走出循环的 final_content 必是最终回答；中间轮的值被下一轮覆盖，模型调工具前的话只进 messages 不作答；超时/断连/熔断属异常路径，返回的是已收到的半截或空串。调用方各取所需：CLI 不理会返回值（已打印过），服务端拿它装响应体。

### 3. G3 预埋分支的验收：服务没有终端，默认拒绝自动生效

- HTTP 服务没有交互 stdin（systemd/容器/`< /dev/null`），ask_user 的 input() 撞 EOFError → 返回 False → 危险工具全部拒绝——**一行代码没改**，「没人能点头 = 没人同意」语义自动成立。
- EOF 不是「等人没等到」，是确定性的「没有更多数据」：input 本质是读 stdin 文件描述符，读到末尾即抛 EOFError——确定性事实支持立即决策默认拒绝，与超时等待无关。
- 三种 stdin 形态走同一个函数：交互终端（阻塞问真人敲 y/N）／空 StringIO（立即 EOF 拒绝）／真实服务（stdin 关闭天然 EOF）——ask_user 不关心输入从哪来，只关心有没有人说了 y。
- 真机冒烟：后台 uvicorn（stdin 断开）+ 读文件请求 → LLM 收到「用户拒绝执行此工具」如实转述。
- 记录在案：echo=False 下 [需确认] prompt 仍打到 stdout（input(prompt) 的固有行为——替换 sys.stdin 只换读取来源，不换提示输出去向），EOF 后立即拒绝无功能影响；生产可收编进 logging。

### 4. 并发取舍：全局锁串行化

- threading.Lock 包住「取会话 → 跑内循环」全程——同一时刻只有一个请求在跑（吞吐换正确）。不加锁的三种损坏：A 的上下文混进 B 的消息（污染）、tool_calls 与 tool 结果被隔开违反协议（下一次 API 调用直接被拒）、Budget 累加丢失更新。
- 锁保证互斥不保证公平：并发两请求的完成顺序取决于谁先抢到锁，正确性标准是「消息完整无交叉」而非顺序。
- 为什么粗粒度：GIL 只保证单条字节码不撕裂，不保证「取会话 → append → 跑完内循环」多步序列的原子性（与 G3 确认锁同源）——最小正确解是全局一把锁，生产再细化。
- 生产形态：per-session 锁 + 会话存储外置（Redis 原子操作）+ 读写分离。
- pydantic 边界校验免费拿：缺 message 字段 422、类型错 422（校验失败不建会话不烧钱）；空消息显式 400。

### 5. 两层记忆的现场演示

- LLM 调 remember 撞 EOF 拒绝后，第二轮从上下文答出 42、又准确指出长期记忆没写入——「上下文（messages，短期）vs 长期记忆（memory.md）」的区别被模型自己演示了一遍。
- 会话连续性同一现场实证：同 session_id 的两个**独立 HTTP 请求**，第二轮答案依赖第一轮——上下文存在服务端会话表里，不在请求里；session_id 只是取回自己上下文的钥匙。

### 6. 服务如何跑起来：uvicorn、监听与跨 shell

- 启动命令五零件：`PYTHONPATH=src`（bash 专属前缀，PowerShell/cmd 把它当程序名报错——跨 shell 用 `--app-dir src`，uvicorn 把目录加进 sys.path）+ `uv run` + `uvicorn`（独立可执行程序，装在 .venv）+ `模块路径:实例名`（uvicorn 按路径导入模块取 app 对象）+ `--port`。
- 代码里没有 uvicorn 是故意的：app 只定义业务，运行器可换——开发 uvicorn（可 `--reload` 热重载）、生产 gunicorn 多 worker、测试 TestClient；代码内启动是另一种写法：`if __name__ == "__main__": uvicorn.run(app, port=8000)`。与 @tool → loop 的「定义与运行分离」同款思想。
- ASGI 协议是两者的接口：uvicorn 实现服务器侧（收报文 → 按协议解析 → 调 app → 写回 socket），FastAPI 实现应用侧——角色对照 OpenAI 协议之于 messages/tool_calls。
- 监听 = bind 向内核**独占**端口：同端口只允许一个进程 LISTENING，第二个 bind 报 10048（地址已被占用）；netstat 里 `LISTENING + PID` 就是「发往此端口的包归这个进程」的系统级含义。`127.0.0.1` 回环流量不出网卡、只有本机可达（安全默认），`--host 0.0.0.0` 才对所有网卡开放。停止 = Ctrl+C，内存会话表随之蒸发。
- /health 的生产角色：存活探针——k8s/负载均衡定期 GET，失败即摘流量/重启容器（崩溃/死锁/端口假死从外面都表现为探活失败）；sessions 字段是排障信号（只涨不降 ≈ 泄漏）。

### 7. 客户端、文档页与日志分层

- 调用服务的代码是**另一份客户端代码**：服务端与客户端两进程两源码，只靠 HTTP 字节交流，互不知道对方源码存在。
- httpx.post 一行背后：构造报文（请求行 + 头 + 体）→ 建 TCP 连接 → 发送 → 阻塞等响应 → 解析成 r 对象；`json=` 自动序列化并设 Content-Type；`r.json()` 把响应体还原成 dict——发出是 dict、路上是字符串、收回是 dict。
- timeout 是真网络最大坑：httpx 默认 5 秒，LLM 调用撑不到——客户端超时放弃，服务端照样跑完照烧钱。按成本预期给 timeout（探活 5 秒、对话 120 秒）。
- TestClient 是假客户端：进程内直呼 app 的 ASGI 接口，不开端口、不发包、不需要服务先启动——与 httpx 的 client.post 签名几乎一致（刻意设计）；真网络形态比它多出的东西：前置探测（ConnectError → 打印启动命令 → 退出码 2 表示环境错误，与 1 断言失败区分）与 timeout。
- 客户端消费错误的标准姿势：先看 status_code（非 200 才读 detail）——服务端 raise HTTPException 在客户端视角就是 400 + `{"detail": ...}`。raise 与工具层拒绝的区别在受众：HTTP 边界的受众是客户端程序（协议该用状态码），工具层拒绝的受众是 LLM（要看到原因调整下一步，故走正常结果不走异常）。
- 浏览器地址栏 = GET；/docs 与 /redoc 是 FastAPI 自动注册的文档路由，从 /openapi.json 渲染——文档由 pydantic 类型声明自动推导，代码改文档自动同步（类型即契约的另一面）。
- 日志去哪了分两层：uvicorn 自带日志（启动 banner + access log「IP 方法路径 状态码」）默认可见；自己模块的 info **默认不可见**——uvicorn 只给自己的 logger 配 handler，root 保持 WARNING 级且无 handler，info 在级别检查即丢弃，warning 走 lastResort 兜底裸打 stderr。`logging.basicConfig(level=logging.INFO)` 一行放开；生产由部署层收集（systemd→journald / docker logs / 集中式 ELK/Loki），代码只管发日志、handler 决定去向。

### 8. 网络边界：从「只有我能调」到「被任何人调」

- 回环地址即最粗的安全防线：127.0.0.1 时代不需要认证，因为网络边界已把陌生人挡住——**每打开一层边界，就要在下一层补一道**。
- 扩散三步：局域网（`--host 0.0.0.0` + ipconfig 查内网 IP + 防火墙放行）→ 公网三条路：云服务器（标准生产：域名 + DNS + nginx 反代 + HTTPS，此时 uvicorn 反而回归 127.0.0.1 不直接暴露）、内网穿透（ngrok/frp，临时演示）、路由器端口映射（不推荐）。
- 公开前的暴露面对照：无认证 = 陌生人可无限建会话烧提供方的钱（Budget 每会话一本但会话可无限创建）；list_dir / grep / calculate 不在确认清单 = 白名单区内真实文件可被陌生人读；全局锁可被合法请求堵死；明文 HTTP。开放前清单：认证、限流、HTTPS、最小暴露。

## 延伸沉淀：从服务化到产品形态

### 1. 服务化改变了什么：CLI 与服务七维对比

| 维度 | CLI | 服务 |
|---|---|---|
| 调用方 | 人（终端敲键盘） | 任何 HTTP 客户端（浏览器 / curl / httpx / 程序） |
| 生命周期 | 进程 = 一次使用 | 常驻，进程承载成千上万次使用 |
| 状态归属 | 进程级单例（进程即会话） | 按 session_id 分格（进程承载多会话） |
| 输入/输出通道 | stdin / stdout | HTTP 请求体 / 响应 + 日志 |
| 并发 | 天然串行 | 天然并发，必须加锁 |
| 错误表达 | 堆栈给人看 | 状态码 + detail 给程序看 |

三条本质转变：

- **调用方从人变程序 = 协议化**：server.py 约 80 行里 agent 逻辑只占 1 行（run_agent_turn 调用），其余全是接口定义——pydantic 校验、路由、序列化都是「程序对程序」的礼仪。
- **进程从一次性到常驻 = 会话降级为资源**：会话从「进程的存在方式」降为「进程里的一种资源」，锁、内存取舍、Redis 迁移全部长在这条线上。
- **通道换掉、防线零改动 = 正交性实证**：G1-G4 长在内循环层，服务化长在外壳层——EOF 默认拒绝语义在新形态下自动成立，是分层设计提前买到的保险。

CLI 与 HTTP 是同一个 agent 的两个薄入口，共享全部核心；每个阶段养的东西没有因下一阶段作废——学习路径每一步是累加不是返工。

### 2. 交付形态与发布

- 术语：**发布（release/publish）** 把软件包交给用户或渠道；**部署（deploy）** 把服务放到运行环境跑起来。SaaS 通常只部署（给 URL 不给码），开源 CLI 通常只发布（给码自己跑）。
- 形态矩阵：本地 × 人用（CLI 工具 / 桌面 App）、本地 × 程序用（库 / MCP / 本地服务）、云端 × 人用（Web 应用）、云端 × 程序用（HTTP API，G5 所在格）。
- Python 包安装链：`[project.scripts]` 入口点（命令 → import 包调 main）→ `uv tool install -e .`（独立环境 + PATH 启动器 + editable 源码链接，改源码全局命令立即变）→ `uv build` 产出 wheel / tar.gz → `uv publish` 上 PyPI。
- PyPI 纪律：name 全站唯一；同一版本号永不重传（版本永久占坑防供应链投毒，改码必 bump version）；发布即源码公开（发前查敏感信息）；TestPyPI 演练场先走全流程。
- 形态家族：wheel 包 / PyInstaller exe（免 Python 环境，代价体积大与杀软误报）/ Docker 镜像 / MCP server（宿主-能力分离）/ GUI 壳；git 直装 `uv tool install git+https://...` 是不发版的轻发布。
- 与 npm 一一对应：registry / 包管理器 / 锁文件 / uvx ≈ npx；差异两点——隔离（node_modules 天生项目隔离，Python venv 是历史补丁）与删除政策（npm 可 unpublish，PyPI 版本占坑）；共同攻击面 typosquatting（抢注热门包的错拼名）。
- 商业分水岭：服务化 = 提供方出 API key、收费、数据在提供方（控制权强）；本地安装 = 用户自带 key（BYOK）、数据不出本机（版本散落升级难）。**API key 在谁手里基本决定商业模式**——G3 的 Budget 在服务形态下是钱的闸门，在本地形态下只是用户自控工具。

### 3. agent 产品形态：自主性光谱

对话助手（ChatGPT / Claude.ai，人驱动每轮，agent 性 = 会调工具）→ 编码智能体（Claude Code / Cursor，终端工作面自主多步，关键动作问人——本项目即其原理教学版：工具循环 = 心脏、G3 = 权限确认、G1 = 工作目录边界）→ 深度研究（DeepResearch / Manus，给目标自主跑几十分钟——MAX_STEPS + Budget 放大几百倍再加规划反思）→ 垂直工作流（客服 / 合同审查 / Coze / Dify，场景收窄重可靠与审计，API 服务嵌业务系统）→ 后台无人值守（定时巡检对账，关键不在聪明在兜底：熔断 / 重试 / 降级 / 留痕）。

- 交付形态横轴上每个格子都有 agent 产品：Web 服务（ChatGPT）/ CLI（Claude Code）/ IDE 插件（Cursor）/ 桌面 App（LM Studio）/ MCP 插件（FastMCP server，宿主-能力分离）/ 设备端（Siri，端云结合）。
- 多智能体不是新心脏：把单循环复制成多份再编排（规划者 → 执行者 → 审查者），langgraph / hello-agents 在依赖里待命。
- 所有形态共用同一颗心脏（LLM 流式决策 + 工具调用 + 结果回传的 while 循环），差异全在四个外围件：工具集大小、自主性参数（MAX_STEPS / Budget / 确认策略）、交付壳、编排层数。
