## H1 数据库只读工具：给 agent 一个只读数据出口

> 记忆钩子：**连接即打开文件；schema 链接不全量塞 prompt；预检管友好拒绝、ro 管底线；种子固定可断言。**

### 1. 定位：生产形态与学习版映射

- 生产形态 = 真实业务库 + 只读账号连接：agent 不掌管数据库，只拿一个**只读的数据出口**——查数可以，写数须人工在数据库端操作。
- 学习版映射：SQLite 文件库（db_seed 幂等重建）+ URI `mode=ro` 连接。"只读账号"由连接参数模拟，写不进去由数据库内核保证。
- SQLite 是嵌入式数据库：没有服务端，**连接 = 打开一个文件**（与 MySQL/PostgreSQL 需要 host/端口/账号的本质差异）；普通 `sqlite3.connect(路径)` 默认读写且文件不存在会自动创建。

### 2. 数据侧：种子固定可断言

- db_seed.build() 幂等重建：先 `unlink` 删旧文件再建，`executescript` 跑建表 + 种子，`commit` 后 `finally` 关连接——多次执行结果一致，谁在何时跑验收起点都相同。
- 种子数字固定（金牌 3 人、最低库存唯一、订单 18 行）→ LLM 端到端验收有**确定性判定依据**：模型回答不可预测，库的状态可精确预知，"答对数"才能变成硬断言。
- 元数据表 `sqlite_master` 是每个 SQLite 库自带的说明书：所有表的名字与 CREATE 语句原文都在里面，schema 工具直接查它。

### 3. schema 链接：按需取结构，不全量塞 prompt

- 两步用法（写进工具描述，模型照做）：`db_schema()` 看有哪些表 → `db_schema(表名)` 看字段定义与行数 → 再写 SQL。
- 对比"全库结构塞进 system prompt"：表少无感，表多则 prompt 被结构淹没且多数轮次用不上——链接式让模型按需取，上下文只装当前要用的。
- 表名参数同样来自模型（不可信输入）：先参数化查询（`?` 占位符）验证存在于 sqlite_master，存在才允许 f-string 拼接 COUNT SQL——**先验证再使用**，与 G1 路径校验同源，手段换成参数化（代码与数据分离，值永远只当值执行）。
- 工具返回的末句是模型下一步的路标：「用 db_schema(表名) 查看具体字段」——工具返回不只给人看，也是模型上下文，末句决定模型的下一步行为。

### 4. 只读双防线：预检管友好拒绝，ro 管底线

| 防线 | 机制 | 职责 |
|---|---|---|
| 第 −1 道 | 工具描述写明「只读、写会被拒」 | 生成前教育，让模型少犯错 |
| 第 1 道 | `_check_readonly` 白名单预检 | 友好拒绝 + 教模型自救 |
| 第 2 道 | `mode=ro` 连接 | SQLite 内核硬保证，安全底线 |

- 预检两步：剥注释（`--` 与 `/* */`）取首词 → 首词须在白名单（SELECT / WITH）；再查中间分号拦多语句。**白名单即能力集**（G2 同源）：只认好词，不枚举坏词。
- 误报从宽：字符串常量含分号也被拦——预检层宁误拒不误放，硬兜底在 ro 层。
- 纵深防御的覆盖边界：SQLite 允许 `WITH t AS (...) DELETE FROM ...`（CTE 后跟写语句）——首词 WITH 在白名单内预检放行，由 ro 连接内核拒绝。处置：不收紧预检（保住合法 CTE 查询），接受**两道防线覆盖面不等同**，行为固化进 step6 [5a]。
- 拒绝语义同 G3：错误串当工具结果回传，循环不断，模型看到原因向用户解释或改写。

### 5. 结果格式化：工具自带边界

- `fetchmany(DB_MAX_ROWS + 1)`：多取的 1 行只用于判断「还有更多」，提示模型加 LIMIT——比 fetchall 内存安全（无 LIMIT 的查询不会吞全表）。
- 表头来自 `cur.description`（DB-API 标准属性，每列七元组取第 0 位列名）——没表头模型只能猜列含义。
- 单元格 60 字符截断、NULL 显示为字面 NULL（`str(None)` 是 "None"，会与内容混淆）——与 MAX_MATCHES / MAX_READ_CHARS 同思想：**工具自带边界，单次结果不撑爆上下文**。
- 管道分隔纯文本输出：token 最省、结构够清楚（JSON 会重复字段名）。
- 空结果与 SQL 报错都带自救指引（「换个条件 / 先 db_schema 确认字段」）——错误串即教材。

### 6. 验收设计：确定性优先，LLM 端到端收尾

- step6 分两部分：确定性验收（[1]-[5]，零 API 成本、秒级可重复）+ `--live` LLM 端到端（[6]-[7]）——CI 门禁（H7）只能跑免费部分，分离是前置设计。
- [4] 八类写攻击全拦经预检：经典 CRUD + PRAGMA / ATTACH（有副作用的非 CRUD）+ 注释藏写 + 多语句；每条单独打印，哪条漏拦一眼可见，failures 只记汇总。
- [5a] / [5b] 纵深防御两个角度：预检放行的 WITH 夹写被 ro 硬拦（含对照组：合法 CTE 不受影响）；绕过预检直接在 ro 连接写被内核拒绝且数据无损——防线不依赖调用者自觉。
- --live 断言哲学：**测行为不测措辞**——LLM 输出逐次不同，只断言三件确定的事：请求成功、回复非空（模型在解释而非执行）、数据无损。
- 聚合查询语义：`COUNT(*)` 无论命中多少行**永远返回一行**（WHERE 1=0 只是值变 0，结果集不空）——空结果断言要用 `SELECT *`。
- mark() 攒 failures 最后汇总 + 退出码 0/1：人看打印、机器看退出码，H7 门禁直接消费。

### 7. GUI 查看：DBeaver 连 SQLite 文件

- 嵌入式库无服务端，连接配置只有「路径」一项（SQLite 类型在「嵌入式」分组）；表结构 / 数据浏览 / SQL 编辑器即日常查数三件套。
- 纪律：GUI 默认可写模式，翻看与 SELECT 随意，**UPDATE/DELETE/INSERT 留给重建脚本**——改了种子数据，step6 的确定性断言就不再成立；改坏跑一遍 `uv run python -m security_serve.agent.db_seed` 幂等重建即恢复。

## H2 Docker 化：交付物从代码包升级为环境包

> 记忆钩子：**程序五层叠，容器装前四层；配方进 git 环境可复现；build 造类、up 造对象；URL 是契约，四处对齐动一则断；镜像入仓库才成制品；compose 声明服务，K8s 声明舰队。**

### 1. 概念层：镜像、容器与适用判据

- 程序五层叠：代码 / 依赖 / 运行时 / 系统库 / OS 内核。传统部署只交付第一层（环境靠目标机器现凑），容器把前四层一起打包——**交付物从"代码包"升级为"环境包"**，"在我机器上是好的"从此是镜像问题，不再甩锅环境。
- 镜像 = 环境快照（只读模板，类比安装包）；容器 = 镜像的运行实例（类：对象）。文件系统、进程、端口互相独立，一台机器并行多容器互不干扰。
- 容器 ≠ 虚拟机：VM 连内核一起装（GB 级、分钟级启动），容器共享宿主内核只带用户态（MB 级、秒级启动）——VM 是独立小楼，容器是大楼里的房间。
- 因果链：Linux 容器必须有 Linux 内核 → Windows 跑 Docker 先要有 Linux 环境 → WSL2（微软内置的轻量 Linux VM）提供内核，引擎装在 WSL 里。不是"让两套系统都能启动服务"，而是"给容器供给它必需的 Linux 内核"。
- **适用判据 = 应用形态**：容器化的价值在"环境进交付物"，常驻服务 / 微服务 / 需要弹性扩缩 → 容器化；纯静态资源 → 介质包反而更轻。公司前端走"zip 介质包 + Ansible 解压到虚机"，后端走"镜像 + harbor + K8s"，正是按这条判据分流的两种形态。

### 2. 环境层：WSL2 + Docker Engine 直装

- 路线选择：Docker Engine 直装而非 Desktop——免费无许可顾虑、形态贴生产（服务器只有引擎不带桌面）、WSL2 Ubuntu 前提现成。
- **daemon（dockerd）= 引擎本体的进程名**：CLI 命令只是遥控器，真正干活的、持有全部状态（镜像库、容器生死、端口转发、探针、日志）的是常驻后台的 dockerd——Unix 服务命名习惯词尾加 d（mysqld / sshd 同族），Windows 对应概念叫"服务"。`docker version` 的 Server 段即 daemon 自报；`daemon.json` 是它的配置（改后需重启 daemon）；daemon 不在时一切命令报 `Cannot connect to the Docker daemon`。
- `wsl -u root`：从 Windows 侧免密以 root 操作 WSL 内服务（装引擎、改配置、看 journalctl）。
- 国内双加速：镜像拉取配 `/etc/docker/daemon.json` 的 registry-mirrors（官方源域名解析被污染直连超时，加速器绕行）；pip / uv 走 Dockerfile 内 `UV_DEFAULT_INDEX` 清华源——**拉镜像与装依赖是两段网络，各自配各自的源**。
- WSL 3.0 两层回收：VM 级空闲回收（`vmIdleTimeout`，只统计活跃用户会话，后台服务不算）+ 服务级按需停启（无会话发行版 systemd 主动停 docker.service）——**后台常驻服务在 WSL 里是"客人"，会话才是"主人"**；学习场景随用随起（compose up 十秒级），长驻则挂持续会话。

### 3. 容器化六阶段：学习版与生产版走的是同一条路

| 阶段 | 学习版（本机） | 生产版（公司后端服务）                      | agent 生产的特殊性 |
|---|---|----------------------------------|---|
| ① 引擎自检 | `docker version` / `hello-world` | CI 节点自带引擎，开发者免装                  | 无差异 |
| ② 写配方 | 三文件进 git | 同款配方进代码仓库                        | 骨架无差；.env 是真金白银的 API key，排除纪律更严 |
| ③ 构建打包 | `docker build -t 名:tag .` | maven 构建 → CI 节点 build           | 测试后加**评测门禁**（分数不达标拦截发布，H7 方向）；模型资源决策：小索引运行时构建、大模型权重绝不进镜像 |
| ④ 运行实例 | `docker compose up -d`（单机单实例） | K8s 声明 replicas:N（多机多实例）         | 调 API 的 agent 与常规服务无差；自托管模型需申请 GPU 资源、按 GPU 节点调度 |
| ⑤ 验收确认 | curl /health + 验收脚本 | 探针就绪链，Service 只给健康实例分流量          | 加 **token / 成本追踪**（H5 方向）；对 LLM API 的限流、超时、重试 |
| ⑥ 入库分发 | 止步本地镜像库 | `docker push` → harbor → CD pull | 无差异 |

六阶段是任何服务容器化的通用骨架；agent 的特殊性不是额外的阶段，而是③⑤两个阶段内部的附加动作，外加 GPU 这个可选维度——流程的"形状"不变，个别格子里的内容换了。

**① 引擎自检**——做什么：确认"拉镜像 → 建容器 → 跑进程"整条链路可用。怎么做：`docker version`，client 与 server **两段都出版本号**才算健康（client 能敲不代表 daemon 活着）；`docker run hello-world`，一条命令完整走一遍拉取、创建、运行、退出。效果：链路通了，后面才有意义。生产对照：引擎装在 CI 节点上（流水线里的 Docker 环境），开发者不必人手一份，但引擎做的事一模一样。

**② 写配方**——做什么：用三个文件声明"排除什么、装什么、怎么跑"。怎么做：`.dockerignore`（不进镜像的排除清单：.env 密钥、运行数据、宿主机依赖）；`Dockerfile`（构建配方：FROM 底座 → 装依赖 → 拷代码 → CMD 主进程）；`docker-compose.yml`（运行声明：端口映射、环境变量、健康检查）。三者进 git。效果：环境定义进版本库，任何人任何机器按配方复现同一环境——uv.lock 锁包、Dockerfile 锁环境，同一思想升一级。生产对照：配方原样进代码仓库供 CI 构建；公司用 `Dockerfile-test` 变体 + `build-arg`（构建参数注入），语法与思想同构。

**③ 构建打包**——做什么：把代码 + 依赖 + 运行时 + 系统库打成分层镜像。怎么做：`docker build -t my-ai-app:h2 .`，末参 `.` 指定构建上下文（当前目录），`-t` 给产物起名。效果：镜像存入本地镜像库；依赖层与代码层分离让层缓存生效——改代码重建秒级。注意 **build 成功 ≠ 可用**：它只证明指令没错、不证明程序能跑，需以最小验证兜底（起容器看日志 / 模块导入）——依赖裁剪后跨包引用的缺失就在这一步显形。生产对照：build 之前流水线先用 maven 完成"拉依赖 + 编译 + 测试"产出 jar（对应本项目的 uv sync + pytest），再由 CI 节点执行同样的 docker build。

**④ 运行实例**——做什么：从镜像实例化容器，对外提供服务。怎么做：`docker compose up -d` 按声明后台拉起 → `docker compose ps` 看状态从 starting 到 **healthy**。效果：容器实例化（进程树 / 文件系统 / 网络三重隔离就位）、引擎建好端口转发规则、探针确认服务真的可用——healthy 比 Up 多一层含义："不只是进程在，是服务可用"。生产对照：运行交给 K8s——不是手敲一条命令，而是声明 replicas:N，**控制循环**持续保证 N 个健康实例（实例崩自动重建、节点宕机自动挪位）；发布走**滚动更新**，逐个替换实例、服务不中断；弹性伸缩就是调 N。

**⑤ 验收确认**——做什么：以客户端身份确认服务语义正确。怎么做：向 `http://127.0.0.1:8000` 发真实请求（curl /health，或既有 HTTP 验收脚本跑完整用例）。效果：端口契约成立、功能可用；同一脚本重跑结果一致，才算收口。生产对照：验收从"一次性动作"升级为"持续性机制"——探针走就绪链（PodScheduled → ContainersReady → Ready）持续体检，Service 只给健康实例分发流量，不健康的自动摘除。

**⑥ 入库分发**——做什么：镜像从本机产物升级为可分发的组织制品。怎么做：`docker login <仓库>` → `docker tag my-ai-app:h2 <仓库>/<项目>/<镜像名>:<tag>` → `docker push`。效果：任何有权限的机器按 tag 拉到**同一个镜像**——"测过的就是部署的"，回滚 = 切回旧 tag。学习版止步于本地镜像库（compose up 直接取用），⑥是学习版与生产版的分水岭。

### 4. build 机制：配方、上下文、镜像库与镜像仓库

- 配方四段骨架：FROM 底座 → 装依赖 → 拷代码 → CMD 主进程，每条指令生成一层。**层缓存按变率排序**：依赖清单先 COPY + `uv sync`（低频变），代码后 COPY（高频变）——改代码时依赖层命中缓存，重建秒级。
- `uv sync --frozen --no-dev --no-install-project`：锁文件思想贯穿——严格按 uv.lock 装包、跳过 pytest 等开发依赖、项目靠 PYTHONPATH 导入不走包安装。
- CMD 两要点：`db_seed` 前置（幂等重建，无状态容器每次启动回到确定种子）；`uvicorn --host 0.0.0.0`（容器内监听 127.0.0.1 端口映射转不进来——G5 回环边界知识的容器版）。
- **上下文打包机制**：`docker build` 末参 `.` 指定构建上下文目录——CLI 按 `.dockerignore` 过滤后，把整个目录**打包发 给daemon**，构建在 daemon 侧执行；`COPY` 只能引用上下文内的文件，项目外的东西带不进镜像（安全边界）。`-t` 仅命名产物；**上下文目录 + Dockerfile 共同构成构建输入**——Docker 没有"项目"概念，只认目录。生产中 build 搬到 CI 节点执行，"打包上下文发引擎"的模型不变，只是引擎换了个机器。
- **配置文件三个读者**：`daemon.json`（引擎自留地，启动时读一次，机器级配置，不在项目内）；Dockerfile / .dockerignore（构建时，daemon 对上下文副本逐条执行）；docker-compose.yml + .env（up 时由 compose 客户端解析，逐条翻译成引擎 API 调用）。
- 配置两种固化时机：Dockerfile 的 `ENV` 在构建期写进镜像层、随镜像分发；compose 的 `env_file` 在运行期注入容器环境变量——容器内代码读取方式不变（`os.environ`），只是值的供给方不同。公司流水线"配置文件修改"节点属前者（按环境出专属镜像，前端 .env 按 mode 出包同款），本项目选后者（一份镜像跑多环境，12-Factor 思想）。
- **本地镜像库**：构建产物持久存放（`docker images` 查看）；`docker compose up` 发现本地有镜像就直接实例化、没有才触发构建——"不 build 直接 up"用的是上次成品。镜像库（成品）与层缓存（中间层）是两个机制：前者支撑免 build 启动，后者支撑增量构建。
- **镜像仓库 = 组织级中转站**：本地镜像库只服务本机，仓库（registry，公司自建 harbor，类比 npm registry——对象从代码包换成环境包）让镜像成为团队共享的制品。寻址格式 `仓库地址/项目/镜像名:tag`（平时写的 `python:3.13-slim` 省略了 docker.io 前缀）；push / pull **按层传输**，只传缺失层——层缓存思想从构建端延续到分发端；制品不可变（同一 tag 内容不变）是"测过的就是部署的"的机制保证。

### 5. 运行机制：实例化、端口转发、契约与多副本分发

- **build 造类，up 造对象**：镜像不会自动变成服务，`docker run` / `docker compose up` 的那一刻才实例化。
- 容器 = 四组内核级隔离资源：独立进程树（CMD 是 1 号进程，主进程退出容器即终止，所以 CMD 必须前台运行）；独立文件系统（镜像只读层 + 容器读写层，写时复制、不污染镜像）；独立网络命名空间（有自己的回环和端口空间）；名字与状态机（created → running ⇄ paused → exited → removed）。同一镜像可实例化任意多个容器；容器默认随删随弃——无状态设计（启动时重建数据、状态外置）正是与它配套的活法。
- compose 关键字段：`ports "宿主:容器"`（引擎转发，容器内外同端口）；`env_file`（密钥运行时注入，不进镜像）；healthcheck（容器内探针——服务探针 → 容器探针 → K8s probe，三级火箭中间级）；服务名即内置 DNS 主机名（服务间互访，H4 Redis / H6 向量库的接线已预留）。
- **端口转发三跳（本机实测链路）**：引擎在创建容器时依据 ports 在宿主侧占用端口并建转发规则（iptables DNAT + docker-proxy），容器删除即拆除。Windows 侧请求实际走：`127.0.0.1:8000` → wslrelay（WSL2 自动桥）→ docker-proxy → 容器。
- **端口排他**：同一 (地址, 端口) 同一时刻只允许一个监听者——本地进程与容器映射同权竞争，后到者报错退出；错开端口（如映射改成 "8001:8000"）即可共存。验证脚本打的 `127.0.0.1:8000` 永远命中"当前占着 8000 的那个"。
- **URL 是契约，四个时刻对齐**：① 客户端契约（验收脚本 BASE 写死 8000，当时 Docker 还不存在）；② 服务端承诺（`uvicorn --port` 与 `ports` 对齐同一端口号）；③ 引擎兑现（up 时占端口建规则）；④ 请求发生时按契约拨号。**127.0.0.1 是相对寻址**——每个网络命名空间有自己的回环，同一串 URL 在容器内外指向的不是同一个 socket；契约链四环**动一则断**，改端口必须成对改；`EXPOSE` 纯属声明元数据，实际通路唯一依据是 `ports`。
- 跨形态一致性：同一代码库在进程形态（本地 uvicorn）与容器形态下，G 阶段防线与 HTTP 语义零改动——例如容器没有终端（stdin 关闭），交互式确认闸门读到 EOF 即默认拒绝，G5 预埋分支自动生效。配置外置（env_file）+ 数据外置（启动重建）是两种形态行为一致的前提。
- **多副本下的请求路由**：多实例并存时，前端请求不再直连"某台机器的端口"，而是走路由链：浏览器 → 域名 → Ingress 入口 → Service（稳定虚拟 IP，按标签圈住一组 Pod 做负载均衡）→ 某个健康 Pod。调用方感知到的是"端点不变的弹性服务"，不是某台固定的服务器。
- **多副本的代价 = 状态必须外置**：同一用户两次请求可能落到不同实例，存在实例内存里的会话就"失忆"——会话状态必须放到所有实例共享的存储（Redis）。H2 的多副本认知是 H4 的第一块拼图。

### 6. 容器操作与日志机制

- `docker exec -it 容器 sh`：向运行中的容器**附加**一个新进程（不是接管主进程），退出附加 shell 不影响主进程。退出用 `exit` 或 Ctrl+D（EOF）；Ctrl+C 发出的 SIGINT 对交互 shell 无效——shell 对它免疫是自我保护设计，而 `logs -f`、`tail -f` 这类跟随型进程对 SIGINT 默认终止自己。Ctrl+D 的 EOF 与确认闸门 `input()` 撞到的 EOF 是同一机制：一个主动关 stdin 退出会话，一个因容器无终端被动触发防线。
- 容器日志：引擎把容器的全部 stdout 持续写入日志文件（json-log 驱动）；`docker compose logs` **先回放全部历史、再跟随新增**。日志来源判读：`127.0.0.1` 是容器内 healthcheck 探针的流量，`172.x.x.x`（Docker 网桥网关）是经端口映射进来的外部流量——见到 172 网段即外部请求真进了容器。单容器 `docker logs` 之外，多实例生产的日志需要集中收集——H5 可观测性的方向。
- 镜像与容器生命周期解耦：删除容器不影响镜像（对象销毁、类还在）；`docker run --rm 镜像 命令` 用一次性容器跑任意命令（覆盖 CMD、退出即自动删）——检视镜像内容、跑一次性任务都用它。
- `docker compose up` 对配置未变的已退出容器执行 start（保留容器与日志历史），配置变了才重建（recreate）。

### 7. 容器化对 agent 的意义

- 共性：agent 经 G5 服务化后就是标准后端（FastAPI + uvicorn + /health 探针），六阶段流程全量适用——容器化的所有机制对它一字不差。
- agent 场景的四个特殊角色：
  1. **环境契约**：agent 依赖本地推理栈（numpy / onnxruntime / fastembed），又重又挑版本——镜像把整条依赖链冻成快照，"embedding 可用"从环境问题变成镜像问题。
  2. **安全边界**：模型行为在运行时才确定（调哪个工具、传什么参数，无法静态审计），容器给工具加上文件系统级物理隔离——`read_file` 的可见世界被压缩到镜像圈定的范围，G 阶段代码级软防线之外多一道硬防线；推向极致即用一次性容器执行模型生成的代码（H3 沙箱的方向）。
  3. **架构推手**：agent 的会话记忆放在实例内存里，而容器随生随灭、可多副本——状态外置（H4 Redis）被容器形态逼成必选项。
  4. **评测基座**：种子数据幂等重建（数据确定）+ 容器（环境确定）→ 评测起点与在哪台机器跑无关、分数可比；模型资源与代码分离（rag_index.json 不进镜像、启动时构建），对应生产中"模型权重不进镜像、运行时拉取"的惯例。H7 的 CI 评测门禁建在这块基座上。
- 收束：传统后端容器化主要解决一个问题——环境一致性；agent 场景下容器化同时是**环境契约、安全边界、架构推手、评测基座**——H3 / H4 / H7 分别兑现后三者，H2 是它们共同的地面。

## H3 代码执行沙箱：把模型写的代码关进一次性容器

> 记忆钩子：**模型能写代码那天起，防线从"审查内容"换成"隔离环境"——五道 docker 围栏 + 双层超时，一次性容器跑完即焚；代码走 stdin 不走命令行；rc 是状态、stdout 是内容，单看哪个都会被骗；run 等到底、Popen 启完走；围栏罩容器不罩语言，换语言只换底座。**

### 1. 为什么需要：三个缺口与权限演进三幕

- 没有执行工具的 agent 有三个缺口：**算不准**（LLM 心算无精确保证，多位数乘法、百分比常错）；**析不动**（拿到数据后缺加工手段，排序 / 分组 / 占比这类统计结论做不出）；**验不了**（答案无法自我验证，错了也不知道错）。「查」（db_query / web_search）+「算」（run_python）补齐后，agent 才是完整的数据分析助手——「这份数据的统计结论」类问题从做不到变成一条工具链。
- **普通工具 vs 执行工具的本质差异**：普通工具是**填空题**——参数固定、行为由开发者定义，防线只需校验输入（白名单、路径检查）；执行工具是**作文题**——模型提交整段代码，行为由模型现场定义，输入校验失效，**防线只能换形态：隔离环境**。
- ast 白名单（safe_eval）的天花板是**图灵不完备**：无变量、无循环、无数据结构、无标准库——表达力残缺是根因，「逐个算太慢」只是表象。统计 / 占比 / 排序 / 分组这类真实需求，白名单形态永远做不了。
- **权限演进三幕**：裸 eval（模型代码直接跑在主进程，G1 之前）→ ast 白名单（能力圈内执行，安全但残废）→ 沙箱内自由执行（能力全开，环境兜底）。演进的方向不是「更严的审查」，而是「更厚的隔离」。
- **防线强度必须匹配能力开放度**：H1 只读工具开放度低（参数级），白名单预检 + ro 连接足够；执行工具开放度高（任意代码），只有环境级隔离兜得住——同一个安全思想在不同开放度下的两种形态。

### 2. 形态与五道围栏：环境级防线，零自研

| 围栏 | docker 参数 | 拦什么 |
|---|---|---|
| 断网 | `--network none` | 数据外传、SSRF、连宿主内网 |
| 纯净文件系统 | 不挂载任何目录、不传 `-e` | 读业务代码、读密钥 |
| 内存上限 | `--memory 128m` | 内存炸弹 |
| CPU 上限 | `--cpus 0.5` | 烧 CPU 的计算 |
| 进程数上限 | `--pids-limit 64` | fork 炸弹 |

- 容器形态：`docker run --rm` 一次性容器（python:3.13-slim 纯净底座，攻击面最小），主进程 `timeout 10 python -`，跑完即焚。**五道围栏全是 docker 原生参数，零自研检查**——自己写的 Python 层检查是应用层的，理论可绕过；namespace 与 cgroup 是内核层的，进程在容器里物理绕不过。与 H1「预检管友好拒绝、ro 管底线」同一思想，这里把底线直接做到最厚。
- **多道围栏的语义是竞速兜底：谁先触发听谁的**——fork 炸弹造出的每个进程都有内存足迹，往往在撞到 64 进程上限之前先撞 128m 内存墙。防线设计认结果不认路径：任意一道触发即达目的，「炸不动宿主」不依赖「哪道围栏拦的」。
- 内存围栏的真实行为：cgroup 限额 + 虚拟内存 overcommit 组合下，`[0]*10**9` 这类申请常常 malloc 先"成功"、真正触碰内存页时被 **OOM killer 直接 SIGKILL（退出码 137）**，Python 层的 MemoryError 反而没机会抛——识别内存超限不能只盯一种表象。
- **双层超时，杀在容器内**：外层能杀的只有 wsl/docker CLI 进程——CLI 死了容器还在 WSL 那头跑，死循环容器泄漏堆积；容器内 GNU timeout 杀的是 python 主进程，主进程一死容器退出、`--rm` 自动清理，闭环完整。外层 subprocess timeout 只做兜底（容器启动卡死等异常路径）。
- **代码经 stdin 喂入（python -），不落盘**：容器里没有模型控制的任何文件，文件系统围栏没有开口子；`input` 写完自动关闭 stdin（EOF），python 收到 EOF 才开始执行——代价是沙箱内 `input()` 必抛 EOFError，而「沙箱代码不交互」本就是合理约束。
- **命令行零痕迹**：cmd 用列表逐词直传 OS、不经过任何 shell（列表形式没有引号转义、没有 `;` `|` 语法）；模型代码走 stdin 数据流，在命令行上找不到影子——**代码作为数据进容器，而不是作为命令进 shell**，shell 注入面被结构性排除。
- **「不传 -e」的链路语义**：子进程默认继承父进程的全部环境变量、同一文件系统、同一用户权限——**隔离是容器的属性，不是子进程的属性**。密钥没漏进容器靠链路两层「不传」：Windows→WSL 不传（WSLENV 未显式设置）、WSL→容器不传（无 `-e`，围栏 2 的刻意设计）——最后一跳是唯一主动锁死的一跳，也是变量进容器的唯一一门。

### 3. 执行器设计：退出码语义化与错误串回传

- **returncode 是状态、stdout 是内容**：stdout 是「程序说了什么」，returncode 是「程序怎么收场的」，单看任何一个都可能被骗——脚本抛异常时 stdout 全空（错误在 stderr）；内存被 OOM 时两者皆空（进程猝死，缓冲区都没来得及刷），唯一证据是退出码。执行器的分工：**rc 分流**（0 / 124 / 137 / 125 / 1 走各自的解读分支），**out 取内容**（正常路径回传模型）。
- **退出码穿透链**：python → timeout（超时改报 124，GNU 约定；否则转发子进程退出码）→ 容器退出码 → docker run CLI → wsl.exe → proc.returncode——每层把自己的退出码交给上一层，一个数字才能分辨五种死法：0 正常 / 1 脚本异常（traceback 在 stderr）/ 124 超时 / 137 被 SIGKILL 即 OOM / 125 docker 自身故障容器没起来。
- **退出码的定义权分层**：跑完 0、未捕获异常 1 是 **CPython 解释器的固定机制**；模型只在显式 `sys.exit(n)` 时拥有最内层的定义权；124 / 137 / 125 是 timeout 工具、内核、docker 的约定，模型完全无法触碰；把数字翻译成「超时 / 内存超限 / docker 故障」诊断串的字典，是执行器写死的。
- **沙箱防伤害，不防撒谎**：模型理论上可在脚本层伪造状态（try/except 吞异常 + `sys.exit(0)` + print"成功"），五道围栏拦不住——围栏防的是**行为越界**（资源 / 网络 / 文件），不防**脚本内的诚实性**；诚实由另一层机制保障（工具结果进上下文、提示词「如实告知禁止编造」、用户验收看事实）。「防恶意行为」与「防不诚实输出」是两个威胁模型，各有各的防线。
- **错误串返回不抛异常**（与 db_query 同源）：工具抛异常会打断 agent 循环，返回错误串则循环继续——traceback 原样回传，模型看报错改代码重试。**这是「自我验证」能力的地基**：能拿到错误，才有下一步修正。
- 工具自带边界：代码长度上限（超长直接拒）、输出截断——与 MAX_MATCHES / FETCH_MAX_CHARS 同思想，单次结果不撑爆上下文。

### 4. 接线：注册表红利与三流全链路

- 注册表红利：`@tool` 一处注册同时产出实现与 schema，新增工具只写一个函数加一个装饰器，loop 层零改动——G 阶段的重构在这里兑现。
- **description 是模型唯一的说明书**：模型看不见 sandbox.py 的代码，何时调（统计 / 占比 / 排序 / 分组）、怎么调（先 db_query 查数、结果写字面量、必须 print）、何时不调（纯算术用 calculate）全写在这段描述里——工具描述就是面向模型的提示工程。
- **提示词分流**：纯算术给 calculate（进程内 ast 白名单，微秒级），数据计算给 run_python（起容器，秒级还吃资源）——不分流则算 2+3 也起一个容器。分工写进 system prompt 工具优先级第 4 条，与工具描述口径一致。
- **一次执行，三流并行**：命令流（cmd 列表描述进程树：wsl → docker → 容器 → timeout → python -）、数据流（`input=code` 经 stdin 管道贯穿四层）、结果流（stdout / stderr / 退出码反向回流）。**docker run 语法的分水岭是镜像名**：左边是引擎解析的配置，右边整体是容器主进程命令行（覆盖镜像自带 CMD）——timeout 是容器内 Linux 的工具，与 Windows、与 Python 侧都无关。
- **WSL 两个身份**：WSL2 本体 = Windows 内置的轻量 Linux VM（真 Linux 内核 + 完整环境，Docker Engine 的宿主）；wsl.exe = Windows 侧操作它的遥控器（`wsl` 进交互 shell、`wsl <命令>` 送命令执行完返回、`-u root` 指定身份）——wsl.exe 自己不执行任何东西，只是跨系统电话线。

### 5. subprocess 知识：run 与 Popen 的分工

- **run 是 Popen 的同步封装**：内部创建 Popen 后阻塞到底——自动收完输出（内部 communicate 处理了管道读写时序）、超时替你杀进程、结果打包成 CompletedProcess 返回。**Popen 是异步原语**：启动即返回、父子并发，等不等、何时等、要不要收尸全是父进程的自由选择（`p.wait()` 随时可补同步点）。一句话：run 强制同步，Popen 给你异步的自由。
- **「后台」不等于「永生」**：Popen 子进程活多久由它自己的代码决定——`while True` 监听 stdin 的 MCP server 真常驻（直到宿主 terminate）；短命令几秒自退，变僵尸进程等父进程 wait 收尸。Popen 模式下父进程欠一个收尾责任（communicate 或 wait），否则 Unix 留僵尸、Windows 漏句柄。
- 死锁坑：Popen + stdout=PIPE 时先 wait 再 read，子进程输出塞满管道缓冲区（约 64KB）阻塞在写、父进程阻塞在 wait——互相等死；communicate（以及 run）用多路收发解决。
- **选型判据 = 通信形态**：一次性命令拿结果 → run（沙箱：喂代码、等容器、拿输出，阻塞正是想要的）；常驻双向多轮通信 → Popen（MCP 宿主：server 常驻，stdin/stdout 反复读写几十轮）。run 与 Popen 的关系，和 Popen 与 stdio_client 的关系同构——底层原语 vs 封装层。

### 6. 衔接与生产对照：围栏罩容器不罩语言

- **同一技术的两个用法**：H2 容器给服务造环境（环境契约），H3 容器给代码造牢笼（安全边界）——H2 第 7 节「推向极致即用一次性容器执行模型生成的代码」在此兑现。
- **围栏罩容器，不罩语言**：python 是图灵完备的万能入口（os.system / subprocess 可调起容器内任何二进制——bash、coreutils 全家桶），模型控制不了入口，但入口后面什么都能摸；不管怎么绕，新进程都在同一个 namespace 里，断网 / 内存 / 进程数限制照样生效——防线做在环境层而非语言层的直接红利。
- **换语言只换底座**：想支持 JS / SQL / bash，改 SANDBOX_IMAGE（如 node:20-slim）与主进程命令即可，五道围栏与语言无关、原封不动。生产 coding agent 的沙箱同构：一个装了 bash / python / 编辑器的通用 Linux 镜像 + 容器层围栏。
- 已知限制与生产解法：主进程在 Windows 上靠 subprocess 调 wsl 里的 docker；服务容器化后（H2 镜像内）主进程自己就在容器里，调不到宿主 docker——生产解法是 docker socket 挂载或远程 daemon API（沙箱执行器作为独立服务部署在宿主侧）。
- 收束：H1 证明了参数级防线（白名单），H3 补上环境级防线（围栏）——agent 的工具防线到此两级齐备：**能力圈内的用白名单，能力圈外的用容器**。

## H4 Redis 会话外置：会话存储从进程内存迁移至独立存储进程

> 记忆钩子：**状态存储与应用逻辑解耦（防腐层），存储替换对调用方透明；易失性不变，易失边界从高频重启的业务进程收窄至独立存储进程；进程内锁的管辖域止于地址空间，跨进程协作设施必须共享；按数据温度分层：热数据驻内存存储、冷数据落 append-only 日志；RDB 快照 / AOF 日志，可再生态可关持久化；SCAN 替代 KEYS；SET ex 原子挂载滑动 TTL；compose up ≠ build，接口成功需直查存储层验证。**

### 1. 问题定义：进程内状态存储的三缺陷与多副本约束

- 进程内存 dict 的三缺陷：**进程私有**（多副本部署下状态不共享）、**生命周期绑定进程**（发版 / 扩容 / 崩溃均触发重启）、**无过期机制**（状态无限累积）。H2 的推论「多副本的代价 = 状态必须外置」在此兑现。
- 多副本是 Web 服务的目标部署形态，三个动因：横向扩容（吞吐近似线性）、故障转移（流量切至存活副本）、滚动发布（任意时刻均有副本服务）。副本 = 同一代码的多个实例，由负载均衡分发请求；进程内状态在多副本下产生**非确定性状态丢失**（路由命中已写副本则正常，否则丢失），单副本测试环境无法暴露。
- **易失性分析**：外置后数据易失性未消除，但易失边界从业务进程（高频重启）收窄至存储进程（独立部署、低频重启、restart 策略自愈）——「重启不失忆」的本质是**状态生命周期与应用进程生命周期解耦**。
- 进程内锁的管辖域 = 进程地址空间：各副本持独立锁实例互不约束；且锁解决并发时序问题，不解决数据位置问题。跨进程并发协调（分布式锁）本身依赖共享第三方——**跨进程协作的全部设施（数据、锁、队列）必须位于共享位置**。
- 验收目标「重启服务后仍应答上一轮事实」：重启对象是应用进程而非存储进程；step8 [7] 以两个独立进程模拟副本读同一存储，状态驻进程内存则该断言物理不可满足。

### 2. Redis 概述：单线程内存 KV 存储

- 定位：内存优先的 KV 数据库，读写亚毫秒级；key 空间扁平，命名空间靠前缀约定（`session:{id}`）；连接 URL 四段 = 协议 / 主机 / 端口 / 逻辑库号，主机名随部署形态变化（容器网络内为 compose 服务名即内置 DNS，容器内 localhost 指向自身）。
- **单线程命令处理**：内存读写 + IO 多路复用（epoll）支撑吞吐，串行化天然保证并发安全。代价：KEYS 全量扫描阻塞所有请求（生产禁用）——**SCAN 游标渐进遍历**（count 为提示值非配额、可能重复返回、唯一契约是存续 key 必返回）。
- **TTL**：`SET key val ex` 原子完成写入与过期挂载（两步执行在进程终止时遗留无 TTL 的孤儿 key）；写时重置 = **滑动过期**，活跃会话持续续期；过期由引擎执行，应用层零清理逻辑。与持久化的交互：重启加载时剔除已过期 key——会话 TTL 封顶持久化收益上限。
- **持久化两通道**（学习版关闭）：**RDB 定时全量快照**（二进制紧凑、恢复快、快照间隔内写入丢失）；**AOF 写命令追加日志**（appendfsync 三档 always / everysec / no，默认 everysec 最多丢 1 秒，需定期重写压缩）。决策依据 = 数据可再生化程度；重启优先 AOF 恢复，RDB 适合备份传输。注意：持久化解决进程重启，**named volume 才解决容器重建**（匿名卷随重建更换 = 假持久化）。
- **数据结构即访问模式**：string（本项目全量读写）、list（RPUSH / LRANGE，增量写与滑动窗口）、hash、set、zset——结构选型先于读写实现。
- **连接模型**：TCP 长连接 + 连接池（建连成本 = 三次握手 + auth，池化纳秒级借还）；`decode_responses=True` 自动解码；redis-py 的 Redis 对象为 RESP 协议编解码器 + socket 收发，不持有数据。

### 3. 实现：防腐层、序列化边界与编排

- **防腐层**：session_store.py 为全项目唯一 Redis 依赖点，三函数封装存储语义——`save_session`（SET+ex 原子写入并挂 TTL）、`load_session`（None 统一「未写入」与「已过期」两态）、`count_sessions`（SCAN 计数供 /health）；存储替换不波及业务层。
- **序列化边界**：JSON 仅支持纯数据，Budget 以 `to_dict` / `from_dict` 跨边界——**状态与行为分离**（方法两端同源无需迁移，仅迁移状态字段）；pickle 因反序列化代码执行风险与跨版本兼容问题弃用。一对方法即 Budget 的持久化 schema。
- server.py：`load → 执行 → save` 替代 dict 读写；进程内锁保护读-改-写序列的原子性（Redis 自身线程安全，锁针对中间态）；已知边界：多副本并发写同一会话为 last-write-wins 覆盖，生产解法 per-session 分布式锁。
- **配置注入三层**：env_file（机密）→ environment（部署拓扑确定值）→ 代码默认值（本地形态兜底）；REDIS_URL 属拓扑值（容器形态仅一个正确答案），置入 .env 会引入配置错误面；environment 优先级高于 env_file。
- **编排**：redis 服务（command 关持久化、`redis-cli ping` 探针、unless-stopped 自愈、端口映射供宿主访问）+ app 注入 REDIS_URL + `depends_on: service_healthy`——启动 ≠ 就绪，探针通过才放行（compose up 输出即依赖链：Created → Waiting → Healthy → Starting）。**restart 策略边界**：仅覆盖进程退出，不覆盖存活但不可用（假死需探针与编排介入）。
- **up ≠ build**：依赖或代码变更后须 `docker compose build`；旧镜像旧代码下接口仍 200，**接口层成功不证明存储层生效**——改造验证须直查存储层（redis-cli 查 key 与 TTL）。层缓存按输入变更失效。
- **写入时机**：请求级落盘（每请求结束一次 save）——以崩溃损失窗口换写入次数；消息级落盘写次数翻倍，会话场景请求级够用。
- **演进路径**：string 全量读写 → list + RPUSH 增量（写复杂度 O(全量) → O(增量)，LRANGE 天然滑窗，多命令需 pipeline 保原子）→ 进程内缓存（多副本一致性：短 TTL 缓存 + 写后自更新）。按需求信号逐级升级，未触发的层即过度设计。

### 4. 存储选型：访问模式决定存储类型，数据温度决定分层

- **四问定访问模式**：① 读写拓扑（单写者 / 多副本）② 数据生命周期（进程内 / 跨重启 / 有时效 / 永久）③ 恢复粒度（续聊 / 状态回放 / 事件审计）④ 读写模式（全量 / 增量 / 热点 / 条件检索）。选型由访问模式推导。
- 形态对照：

| agent 形态 | 会话存储 | 代表 |
|---|---|---|
| 单机 CLI / 本地 | 本地 JSONL append-only 事件日志 | Claude Code |
| 多副本 Web 服务 | Redis：string + TTL → list 增量 | 本项目 H4 |
| 工作流 / 状态机 | checkpoint 全量状态快照落库 | LangGraph（time-travel / 中断恢复）|
| 平台托管 | thread 对象，数据主权换零运维 | OpenAI threads |
| 跨会话记忆 | 事实提取 + 向量 / 图存储 | Mem0 / Letta |

- **客户端会话模式**（状态存用户端：JWT / localStorage）真实存在，服务端完全无状态；失效前提：① 信任边界（客户端可篡改 = 注入面 + 上下文出域）② 服务端私有状态不可托管（Budget / 工具结果归属服务端）③ 多端一致（需要服务端事实源）④ 流量（每请求全量上传）。适用于纯前端场景，不适用于带工具与预算的服务端 agent。
- **Claude Code JSONL**：append-only 事件日志——uuid/parentUuid 链（分支回溯）、API 响应原样嵌入（model/usage 可审计）、运行时状态入账、从不清理；**存储全量与上下文窗口分离**（compact 为摘要视图）。成立前提：单写者、读极冷（仅 resume 读取）、零依赖、可检索。
- **温度分层**：热数据（每请求读写的工作集）驻内存型共享存储；冷数据（事件日志 / 审计 / 计费）异步落 append-only 文件——同一服务内两层并存。本地文件方案在多副本 Web 场景的失效点：本地盘副本间私有、共享须 NFS 且**文件锁在网络文件系统上不可靠**、热数据经网络文件系统读延迟不可接受、TTL 需自实现清理任务。
- 通用纪律：**追加优于重写**（JSONL / AOF / RPUSH / 消息表 INSERT 同构）；**存储全量与模型窗口分离**；**防腐层隔离**；**每层设施对应需求信号**。

### 5. 收束：无状态化

- 状态外置后 app 成为**无状态服务**：副本可任意伸缩与替换，扩容从风险操作变为常规操作。验收三层证据：确定性断言（存储机制，免费可回归）+ LLM 端到端（真实链路，含跨重启）+ 手动重启演示；**模型行为是端到端的额外变量**（工具拒绝被模型泛化为事实不可知，需措辞约束）——验收结论须来自分层证据，不能来自单一成功表象。
- 外置母题：H1 查询外置（数据库）、H3 执行外置（容器）、H4 状态外置（Redis）——不可控能力下沉至专职进程，主体收敛至最小面。

## H5 可观测性：系统行为事件化为结构化数据，三问由日志聚合作答

> 记忆钩子：**可观测性 ≠ 打日志，是行为事件化——每行一个 event、业务数据进 extra 字段、JSONL 落盘，机器可聚合而非人眼可读；print 的三缺陷：不可聚合、无级别去向、生命周期绑终端；request_id 是贯穿链：ContextVar 横切零侵入，线程池老 API 不复制 context 须 copy_context 显式带走；中间件 add_middleware = insert(0)，后注册者外层先执行，每层 BaseHTTPMiddleware 独立 task、context 快照隔离——注册顺序即数据可见性；计时用 perf_counter 单调时钟、finally 兜异常路径，故障请求从统计消失是最危险盲区；看 p95 不看平均（长尾被平均掩盖，实测 p50≈3.0s p95≈7.0s）；流式 usage 默认不发，stream_options 显式要，两种形态捕获代码在 choices 判断之前；成本记账双口径：精确优先、估算兜底，对账实证 tools schema 漏计占 85%、LLM 占 99% 延迟；聚合查询容忍日志 schema 版本演进；生产对照 ELK/Loki（引擎换、分组逻辑不变）与 OpenTelemetry（trace_id 即 request_id 的生产版）。**

### 1. 问题定义：三问即验收标准

- 可观测性的验收不是「日志有了没有」，而是三问能否从数据作答：某时段 p95 延迟多少、哪个工具最慢、哪个会话最烧钱。答案全在事件字段里：问① ← `http_request` 行（path/duration_ms）；问② ← `tool_call` 行（tool/duration_ms）；问③ ← `chat_in`（session_id）join `llm_usage`（total_tokens）——**缝合两行的 join 键正是 request_id**，贯穿链的价值在收口时兑现。
- print 的三缺陷：人读字符串机器不可聚合；无级别、无去向、无字段概念；stdout 生命周期绑终端（服务形态无人盯屏）。改造不是给 print 加参数，是换机制：`log.info(msg, extra={...})` → JsonFormatter 出口统一。
- 收口物 step9_summary：三问聚合查询配方，各问样本非空才算 PASS——「能回答」是标准，不是「打印了查询」。查询即证明：结构化日志 + 分组聚合 = 运维三问的答案。

### 2. logging 机制：两道闸、三件套、一个分界

- logger 树：同名唯一（内部注册表），层级 propagate 向 root 冒泡；每 logger 一份级别，判定走**两道闸**——logger 级先拦、handler 级再拦，任一不过即弃。
- 三件套各管一段：Handler（去向：文件 / 控制台）、Formatter（格式）、Filter（内容）。应用在入口配置 root（logsetup 的 setup），**库代码只 getLogger 不 configure**——配置权归应用是 logging 的分界纪律。
- lastResort 兜底：零配置时 warning 以上走 stderr——裸 INFO 消失的真相是最后一道内置 handler 在拦。
- **uvicorn 的 access logger propagate=False**：自带 handler 自产自销，不冒泡进 root——要集中收集须显式打开。「日志没出现」先查两道闸与 propagate，再查代码。

### 3. JSON 结构化日志：人机双口

- 同一事件两种视图：控制台口人读格式（排障现场），文件口 JSONL（聚合数据源）——双 handler 挂同一 logger。
- **业务数据进 extra 字段、不进 message**：message 留人读描述，聚合靠字段；event 是行类型的统一入口，一行一事件。事件类型即数据表：session_new / chat_in / tool_call / llm_usage / http_request / budget_breach。
- 日志即数据：JSONL append-only、从不清理——H4 的存储纪律（追加优于重写、全量存储与视图分离）在观测域同构。

### 4. request_id 贯穿：ContextVar 与线程陷阱

- ContextVar：每执行上下文一份副本；Formatter 出口统一读取，业务函数零参数传递——横切字段的零侵入方案。中间件生成 / 透传（上游 X-Request-ID 优先、截断防超长）、finally reset 防请求间残留、响应头回写供客户端对账。
- **易错：ThreadPoolExecutor.submit 不复制 context**（thread-local 时代的老 API），工作线程读 ContextVar 得 None——`copy_context()` 快照 + `ctx.run(fn)` 把请求上下文显式带进线程；计时器在工具自己的线程里各计各的，无锁无争用。
- 单条日志只有 request_id 没有全维字段：跨行 join（session 归属 ↔ token 消耗）靠贯穿链缝合，字段不必冗余复制——链路标识的唯一性就是 join 能力。

### 5. 中间件机制：注册顺序即数据可见性

- **add_middleware = insert(0)**：后注册的包在更外层、先执行（与直觉相反）；构建时 reversed 从 router 向外包裹，ServerErrorMiddleware 恒最外、ExceptionMiddleware 恒最内。
- call_next：把剩余链路（下层中间件 → 路由 → 端点）扔进新 task，本层在此行暂停，响应头抵达内存流即恢复（body 是异步流）；忘调它请求死在这一层。
- **每层 BaseHTTPMiddleware 跑在独立 task，context 是创建时刻的快照**——外层永远读不到内层 set 的 ContextVar。推论：计时中间件必须注册在 request_id **之前**（成为内层、后执行）才读到 rid；ctx_probe 对照实验实证。
- 计时纪律：perf_counter 单调时钟（免疫 NTP 回拨，time.time 只用于落时间戳）；**finally 兜异常路径**——异常请求记 500 后原样上抛，故障从统计里消失比故障本身更危险；round 3 位保住微秒级工具耗时（round 1 位全成 0.0，聚合失义）。

### 6. 延迟分位数：看 p95 不看平均

- 长尾被平均掩盖：99 个 10ms + 1 个 10s，平均 110ms 显得健康，但 1% 用户在等 10 秒；agent 服务的 LLM 调用天然长尾，平均值几乎无信息量。
- 最近秩法：`idx = ceil(p*n)-1` clamp 进 [0, n-1]，无插值零依赖，与 Prometheus histogram bucket 语义近似（bucket 上界即「不慢于」）。
- 实测分布：p50≈3.0s、p95≈7.0s、max≈7.0s——p50 与 p95 之间 2.3 倍的长尾形态才是容量与体验决策的依据。

### 7. 成本归因：双口径记账与对照实验

- **流式 usage 默认不发**：显式 `stream_options={"include_usage": True}` 向服务端要收尾块，不带则恒 None。两种流式形态——OpenAI 标准 = 无 choices 的独立收尾块；部分网关（Anthropic 兼容层）挂在最后一个普通 chunk 上——捕获代码放在 choices 判断**之前**，两形态通吃（usage_probe 对照实验实证：不带参数则完全没有）。
- Budget 双口径：`record_tokens`（真 tokens，精确）优先，拿不到 usage 回落 `record`（字符折算估算）——**精确口径优先、估算护栏兜底**，观测升级不破坏可用性。对账实证：真 2289 vs 折算 610——**tools schema 漏计占 85%**：每轮请求都重发 schema，是固定大头成本；agent 的钱 99% 花在 LLM（耗时 6.4s vs 工具 0.1ms），优化方向由数据指认而非直觉。
- 测试分层与假件纪律：默认模式 patch 系统边界（LLM client / session 读写）精确断言逻辑（used_tokens == 240），--live 起真 uvicorn + fakeredis TcpFakeServer（讲真协议的内存 Redis）验真实兼容性——**只 mock 系统边界，被测对象真身跑**；patch 使用方模块而非定义方（from-import 是值拷贝）。
- 观测代码自己也会算错账：health 轮询行混入「端到端」求和，数字「差不多对」掩盖逻辑错误——**被误差掩盖的错误最危险**，聚合条件必须收紧到 path 级；TestClient 测不到的形态（轮询、真端口）只有 --live 才暴露。

### 8. 生产对照与通用纪律

- ELK / Loki：同样的分组聚合，引擎换、查询逻辑不变——JSONL + 脚本聚合是它们的最小同构物；日志（明细、可追溯）与指标（预聚合、告警）分工，histogram bucket 从中插值出 p95。
- OpenTelemetry：trace_id / span 树是 request_id 的生产版（跨服务、树形、标准协议）——本阶段的手工单链版补的是同一思想：**贯穿链标识 + 出口统一注入**。
- 日志 schema 版本演进：新字段旧行没有，聚合查询须容忍缺字段跳过（step9_summary 问②实测踩中：H5-4 之前的 tool_call 行无 duration_ms，直接下标访问 KeyError）——读自己写的日志也要防御 schema 漂移。
- 验收纪律一以贯之：确定性断言为主（零 API、可回归），LLM 端到端 --live 收尾验兼容性；分层证据链（字段齐 → 精确记账 → 真实网关 → 三问作答），结论不来自单一成功表象。
