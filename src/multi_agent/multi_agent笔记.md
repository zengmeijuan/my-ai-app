# multi_agent 笔记（里程碑 E：多 agent 压缩版）

> 里程碑 E 学习笔记，对应 README「里程碑 E：多 agent 压缩版」。
> 原则：做小不做大——一个三角色系统足以理解协调问题，不碰 CrewAI 类模板化框架。
> 场景：深度研究——多 agent 三条件（可并行 / 上下文可切分 / 结果易验证）全中的任务。
> 组织原则：每个任务收尾确认后，才把该任务的核心知识点汇总进对应小节；
> 先说清判定准绳（是什么），再讲角色分工（谁是谁），最后落设计要点与实现（怎么用、怎么写）。
> 主线：固定工作流（step0）→ 内容函数路由 supervisor（step1）→ researcher agent 化（E2）→ 并行多实例（E3）。

## E1 supervisor 骨架：多 agent 的判定与 supervisor 的设计（✅ 2026-11-03）

> 产出：step0_fixed_workflow.py（固定工作流基线）+ step1_supervisor.py（最小动态深度研究）。
> 记忆钩子：**agent 数循环体，supervisor 看路由，工序看产出。**

### 1. 什么是 agent，什么是多 agent（本阶段的判定准绳）

**判定一个 LLM 应用是不是"多 agent"，只看两件事：系统里有几个自主循环体，它们之间有没有协调机制。**

**agent 的准绳：LLM 在循环里自主决定下一步。** 三个要件：①有工具（有手）；②有循环
（能多轮执行"调工具 → 看结果 → 调整"）；③自主决策（调什么、何时停由模型定，不由代码定）。
三件齐全的角色是 agent。LLM 只做一次性"输入 → 输出"的环节（改写、判断、综合）称为
**工序**——它是流程中会思考的一步，不是 agent。

**多 agent 的硬标准：agent 实例数 ≥2 + 协调机制。** 三条细则：

- **数实例，不数角色**：同一角色的 N 个并行实例（各自独立的循环、上下文、工具调用历史）
  就是 N 个 agent——Anthropic 多 agent 研究系统的 lead agent + N 个搜索 subagent 即此形态。
  常见形态按两维组合：同构多实例（N 个并行 researcher）、异构各一实例（supervisor + 各带
  不同工具的 workers，langgraph-supervisor 库的默认形态）、混合（编排者 + 并行 agent + 工序）；
- **标签属于系统，不属于成员**：系统里有工序成员不影响它叫多 agent，但工序不计入 agent 数；
- **名字不是判据**：角色名（分析师 / 顾问 / 专家）不产生循环，判定只数循环体。

**本项目锚定**：

- B2 step1 / step4 客服 agent：1 个 ReAct 循环体 → 单 agent 系统；
- B2 step5：主图（call_model ↔ ToolNode 循环）是标准 ReAct agent；藏在 search_knowledge
  工具里的检索子图是带评审回环的工序流水线（rewrite → retrieve → judge，判不够打回改写
  重查、代码封顶 2 次）——子图有循环、出口也读模型输出，但每轮重放的工序固定，judge 只拥有
  既定路径的二选一路由权，不算自主循环体（判定详见 E2 §2）。系统整体是"**agent 调用
  流水线**"的组合；
- E step1：三节点接力 + supervisor 内容路由，循环体 0 个，是多 agent 的形态前身；
  E2 researcher 装上联网工具循环成为第 1 个 agent，E3 并行多实例后达标 multi-agent。

### 2. 系统成员的三类角色：编排者 / agent / 工序

**一个多 agent 系统的成员分三类，判定看"产出是什么、被谁消费"。**

| 角色 | 判定特征 | 本系统 |
|---|---|---|
| **编排者（orchestrator）** | 产出即流程：输出（下一步给谁、给什么指令、何时结束）被条件边直接消费成执行流；无工具、无自身循环（被图调度器每轮调用一次） | supervisor |
| **agent** | 产出是数据 + 拥有自主循环（工具 + 迭代决策） | E2 后的 researcher、E3 后的并行实例 |
| **工序** | 产出是数据，单次 LLM 调用 | synthesizer（永远保持工序） |

**编排者与工序的分界**在产出的去向：工序的产出写入 State 的数据字段，被下游节点阅读；
编排者的产出（`next` 字段）被条件边直接消费成执行流——它输出什么，图就走哪里。

**按需 agent 化**：一个角色该不该做成 agent，看任务里有没有"需要工具探索来消解的
不确定性"。researcher 搜什么词、抓哪页、搜几轮事前不可知 → 做成 agent；synthesizer
输入定则输出定 → 保持工序。**自主性是预算：系统的失控面等于各成员自主度之和**，
把它花在真正需要探索的角色上。生产对照：Anthropic 研究系统里 lead 与搜索 subagent
跑 ReAct 循环，综合写报告是一次性生成。

**subgraph 与多 agent 是正交概念**：subgraph 管"一段流程怎么藏"（封装机制），多 agent
管"一队角色怎么派活"（协调拓扑）。subgraph 里装了几个循环体，就承载几个 agent；
选择准绳：调用方只要结果 → 藏进工具或节点（B2 step5 把检索子图藏进 search_knowledge）；
要干预过程（看状态 / 路由 / 打回）→ 摊开共享 State（E 的 supervisor 直接读材料与答案）。

### 3. supervisor 的设计要点：路由决策是内容的函数

**supervisor 的价值判据：路由决策必须"读懂内容"才能做——拆题、判够、判答这三类判断
无法穷举成字段条件，才需要 LLM 出场。**

深度研究场景的三次内容路由：

| 路由 | 判断内容 | 为什么必须读懂内容 |
|---|---|---|
| 拆题 | 把题目翻译成调研指令（查哪些维度、什么算资料齐） | 换一道题，维度划分就完全不同 |
| 判材料 | 读材料判断够不够、偏没偏，决定放行综合或改写指令补查 | "够"是语义判断，字段（有无 research）给不出答案 |
| 终审 | 读答案判断是否直接回答了题目、是否忠于材料 | "答到点上"只能靠理解 |

**directive 机制**：决策的载体是"选节点 + 写指令"。指令写入 `supervisor_note`（TypedDict
覆盖语义，worker 永远只看到当前指令，无需判断哪条最新），worker 按指令干活。检验
supervisor 是否真在读内容的方法：**看两次路由的 directive 是否随内容变化**。

**三阶段结构**：阶段标记（无材料 → 拆题 / 有材料 → 判材 / 有答案 → 终审）用代码 if/else
判断；阶段内的决策（拆什么维度、够不够、打不打回）交给 LLM。原则：**能确定的交给代码，
要理解的交给 LLM**——LLM 的判断力只花在字段判断覆盖不了的地方。

**双层停止条件**：业务熔断 MAX_ROUNDS=2（写进 supervisor 阶段规则，达到上限禁止再派
researcher）+ 框架兜底 recursion_limit。熔断后的行为设计：派 synthesizer 注明材料局限、
**带局限收尾**——用户至少拿到一个答案，且知道它的成色。

## E2 复用 web_search / web_fetch：researcher agent 化（✅ 2026-11-03）

> 产出：step2_research_tools.py——supervisor 与 synthesizer 一字未改，researcher
> 从"靠模型自带知识的工序"升级为带联网工具的 ReAct 子图（系统第 1 个 agent）。
> 记忆钩子：**装手三件套，循环看动作空间；边界靠翻译，环上设熔断。**

### 1. 工具接入三件套：@tool / bind_tools / ToolNode（给模型装手）

模型要用工具，三样东西各归其位：**元数据让模型知道有什么，schema 挂载让模型能发起，执行把意图变成结果。**

- **@tool 装饰器 → 生成工具对象**：从函数自动提取三件套元数据——函数名 → 工具名、
  docstring → 工具描述（模型选工具的唯一依据，要写"什么时候该用我"而非"我干了什么"）、
  参数类型注解 → 参数 schema；原函数体保留为实现。语法要点：参数类型注解必须写全
  （模型只看得见 schema，看不见实现）。复用现有函数就写一行薄包装
  （`return _web_search(query)`），工具视角的元数据与既有实现由此分离；
- **bind_tools → 把 schema 挂上模型**：将工具 schema 翻译成 function calling 报文格式，
  随每次请求携带。挂上后模型可发起调用：返回的 AIMessage 带 `tool_calls`（工具名 +
  参数字典）。它是调用意图，不执行；
- **ToolNode → 批量执行节点**：接收 AIMessage，执行其中全部 tool_calls，每个结果包装成
  ToolMessage 追加进消息历史。工具结果进消息历史，下一轮模型才能"看到"结果调整策略——
  循环得以迭代的物质基础。

### 2. 循环的判定：有循环 ≠ agent，看动作空间

**判定一个循环是不是自主循环体，看"每轮下一步做什么"由谁决定。**

| | 自主循环（agent ↔ tools） | 流水线回环（评审重试） |
|---|---|---|
| 每轮做什么 | 运行时模型现场选（哪个工具、什么参数） | 编译期画死（固定工序重放） |
| 动作空间 | 开放不可穷举（工具 × 参数 × 顺序 × 轮数） | 封闭二选一（重跑既定流程或停） |
| 模型输出性质 | 动作指令（tool_calls，被工具执行器消费） | 任务产物（判定结论，作数据进 State） |
| 何时停 | 模型自主收手（决定性），熔断只做保险 | 模型投一票，代码封顶 |

例证锚定：B2 step5 检索子图（judge 判不够打回 rewrite、封顶 2 次）与 step0 的 reviewer
（approved 打回 revise、封顶 2 次）结构同构——**读内容的二元评审 + 既定路径的路由权 +
代码封顶**，称**闸门**（工序化的 quality gate）。三类路由型角色由此完整：编排者路由
**别人**下一步，闸门只判**既定流程**要不要重放，agent 决定**自己**下一步。

两个实用判据：

- **输出下游**：被工具执行器消费（tool_calls → ToolNode）→ agent；被条件边/Command 消费
  （goto / next）→ 路由型角色（编排者或闸门）；只作数据进 State → 纯工序；
- **代理判据 grep `bind_tools`**：没挂工具就没有开放动作空间，回边再多也是工序接力。
  bind_tools 是必要非充分条件（极端的固定调用会退化动作空间），根本判据始终是决策自由度
  （调什么、参数是什么、何时停由模型定）。

### 3. 主图与子图的 State 边界：两份独立内存

**主图与子图是两个独立的 StateGraph 实例，各自持有 schema 与 State，运行时是隔离的两份内存——框架不会自动打通。** 交互全部发生在节点函数体内，靠普通函数调用的传参与返回值完成：

```
主图 State ─① 整份作参数传入节点函数 → 函数内读字段
           ─② 手工构造子图入参（入参翻译）
           ─③ 子图 invoke（子图 State 独立生命周期）→ 返回子图终态
           ─④ 函数内提取所需字段（出参提取）→ return 更新包
           ─⑤ 主图 State 按 reducer 合并更新包
```

入参翻译 + 出参提取就是"藏"的成本与收益：子图中间过程在主图 State 里不存在，只有最终产出
进来。State 同构时可编译后直接 `add_node` 免翻译（框架自动共享同一份 State）；不同构且
调用方只要结果时才手工翻译——B2 step5 藏进 @tool、E2 藏进节点函数，同一准绳两处落点。

**节点函数的 return 是增量更新包，不是新 State**：LangGraph 按字段登记的规则合并——
TypedDict 裸字段默认**覆盖**（同名键替换旧值、未返回的键不变，所以节点只 return 自己负责
的字段）；`Annotated[list, add_messages]` 按 reducer **追加**（消息历史）。

### 4. 熔断：带环系统的停止条件

**词源是电气断路器：给一条可能自我延续的执行路径设硬上限，达到后禁止继续、强制改道收尾出口。**

需要熔断的判据：**路径里有环，且每次迭代消耗真实资源**（LLM 调用费 / 时间 / token）。
环上每步是 LLM 决策（概率行为）——可能无限互相打回、agent 收不住手；prompt 写了
"该停就停"也只是概率约束。本项目落点：MAX_STEPS（A）、MAX_REVISIONS（step0）、
MAX_ROUNDS（step1/2）、MAX_TOOL_CALLS（step2）——凡带回边的图，都要回答
"这条路径最多走几次"。

**双层设计**：

| 层 | 控制者 | 熔断后行为 |
|---|---|---|
| 业务熔断 | 代码 / prompt 规则（MAX_ROUNDS、MAX_TOOL_CALLS…） | 优雅收尾（带局限交付） |
| 框架兜底 | LangGraph recursion_limit | 抛 GraphRecursionError |

业务熔断在先（语义层判断该收了，走收尾出口）；框架兜底在后（不理解业务，只防代码 bug）
——**正常流程永远不该触碰兜底层，实际触发即是业务熔断设计漏了的信号**。

**agent 工具预算的双层实现**（E2）：prompt 软引导（系统提示写明预算）+ 结构硬熔断
（条件边统计历史 tool_calls 总数，达标改道 finalize）。finalize 不带工具、裸 `llm.invoke`
强制产出——**机制约束优于格式约束**：不指望模型自律，由图结构接管收手时机。收尾指令追加
在消息历史**末尾**（HumanMessage）：模型注意力对末尾最强，指令贴近生成位置，产出即为目标格式。

## E3 成员契约、停止条件固化与 Send 并行多实例（✅ 2026-11-04）

> 产出：step3_contracts.py——契约集中化、批次熔断代码层固化、Send fan-out 并行多
> researcher。agent 实例数 ≥2，系统自此达标 multi-agent（数实例，不数角色）。
> 记忆钩子：**契约先行，Send 派工；reducer 合并，代码封顶。**

### 1. 成员契约：职责边界 / 输入输出 schema / 停止条件集中定义

**契约先行是协调的前提：supervisor 按契约写工单，worker 按契约交产出，成员之间只通过
schema 交互。** 契约集中定义在代码顶部一屏内，节点函数是实现，必须与契约一致。
每个成员的契约三要素：职责（干什么不干什么）、输入输出 schema（读什么写什么）、
停止条件（何时停）。

**入参走 payload，出参走 State**：Send 派发实例的输入是工单 payload，输出仍按字段
reducer 合并回主图 State——不对称结构。

**工单自包含**：Send payload 之外实例读不到 State 的任何字段，工单必须携带全部所需
（topic 由 supervisor 代码补进每份工单）——这是机制要求，不是风格偏好。

**节点入参的三种形态**：①全 State（普通边调度的默认）；②input schema 投影
（`add_node(input=...)`，入参是 State 的字段子集，最小知识面）；③Send payload
（脱离 State，运行时动态构造，多实例派发专用）。

### 2. Send API：动态派生并行任务

**Send(node_name, payload) 是给调度器的派工指令：以 node_name 为目标、payload 为该
实例的输入，起一个独立任务。** 条件边函数返回 Send 列表即 fan-out——列表多长派几个
实例，同一批次在同一 super-step 内并行执行，全部完成后才走回边进下一 super-step。

与条件边的本质区别：条件边是"**选边**"（候选目标静态已知，选一条），Send 是
"**派生任务**"（数量、输入都运行时才定）。

每个实例完全独立（各自的 ReAct 循环、上下文、工具调用历史），同一角色 N 个并行实例
就是 N 个 agent。并行的实质价值不止加速：**实例互相看不见，交叉验证可纠正彼此的
材料偏差**。

State 适配（并行的必然后果）：

- research 字段加累加 reducer——默认覆盖语义下并行实例互相吞掉，**并行写同一字段
  必须有 reducer**；
- round_count 从"实例自增"改为"supervisor 派发批次时自增"（N 实例算一批）——计数器
  所有权给唯一理解"批次"概念的角色。

统一派发协议：补查派发也组装成长度为 1 的工单列表照样走 Send——节点只有一种输入
形态，不需要兼容"整份 State"与"单份工单"两种入口。

### 3. reducer 与 Annotated：字段的合并规则

**reducer 是"字段收到新值时如何与旧值合成新值"的规则函数**，签名
`(current, update) -> new`；名字来自函数式 reduce（把一串增量归约成一个累积结果）。

- **每个字段都有 reducer**：无 Annotated 时隐式默认覆盖（new = update），
  Annotated 把它显式化；
- **字段级，非调用级**：同一字段全图一条规则，声明在 State 定义处，节点不能临时换；
  只管写不管读；
- **调用时机三处**：节点更新包合并 / 并行更新逐个合并 / 断点恢复后继续累积。

**Annotated 是标准库"类型旁注"机制（PEP 593）**：`Annotated[真实类型, 元数据...]`——
类型检查器只看第一个参数，元数据留给感兴趣的框架在运行时读取
（`get_type_hints(include_extras=True)` / `get_args`）。LangGraph 建图时对每个字段
introspect：旁注里的可调用对象 → 注册为该字段的 reducer。这也解释了 reducer 为何
必须写在 State 类定义里——它是字段属性，不是节点属性。同一模式的其他消费者：
`add_messages`（内置 reducer，按消息 id 追加去重）、pydantic Field 约束、FastAPI
参数声明——"注解即配置"。

**需要自定义 reducer 的判据是更新模式，不是字段格式**：单写入者全量替换 → 覆盖就够；
多写入者各交一块（累积语义）→ 无论 str 还是 list 都必须声明合并规则。设计顺序：
先定数据结构（材料按"份"处理 → `list[str]`，每实例返回单元素列表），再为结构定
合并规则（拼接）。运行时形态：`list[str]`，一元素一份材料；元素顺序是更新到达顺序，
与派发顺序无关，消费侧按"份"处理、不依赖顺序。

### 4. LangGraph 四种路由方式

| 方式 | 逻辑位置 | 目标确定时机 | 独立输入 | 项目实物 |
|---|---|---|---|---|
| add_edge | 图结构，无条件 | 编译期 | 无 | step5 检索子图主链 |
| add_conditional_edges | 图结构上的 router 函数 | 运行时选**既定**边 | 无（靠 State） | supervisor 三阶段路由 |
| Send | 条件边内派发 | 运行时**派生**任务 | 有（payload） | E3 并行 researcher |
| Command | **节点函数内部** | 运行时节点自定 | 无（update 走 State） | B2 step5 judge、interrupt 恢复 |

**Command 与条件边的选型判据：路由依据要不要持久化进 State。** 一次性局部判断
（judge 的 verdict，用完即弃）→ Command 免中转：判断、更新、路由一个返回里完成，
不必为路由开 State 字段；记录在案的编排决策（supervisor 的 next，需留痕对照）→
条件边集中声明，静态拓扑可读。Command 的代价：goto 不出现在静态图视图。

Command 家族能力：`goto`（节点内定向）/ `Command(resume=...)`（interrupt 后人工
恢复）/ `Command(graph=Command.PARENT, goto=...)`（子图内跳父图节点）/ `goto` 接受
Send 列表（节点内直接派发）。四者可组合：E3 是条件边外壳 + Send 内核，B2 step5 是
静态边主链 + Command 收尾。

### 5. 自主性的边界：LLM 定合理值，代码守绝对边界

**能确定的交给代码：凡由 LLM 决定"多少"的地方，代码都要有确定性封顶。**

- **停止条件代码层固化**：轮次比较是纯字段判断，LLM 决策返回后代码检查
  `next == "researcher" and count >= MAX_ROUNDS` 直接改写路由——prompt 规则是概率性
  约束，代码改写是确定性防线。检查位置在 `router.invoke` 之后、返回 updates 之前：
  LLM 的决策先产生（reason 留作观察），代码做最后裁决；
- **任务数量**：拆几个维度是内容判断，交给 LLM（schema description 给范围，软约束）；
  派发前代码截断 `tasks[:MAX_INSTANCES]`（硬上限）。Send 协议对数量无感（动态性
  免费），要封顶是因为每个实例背后是真实调用成本；
- 与熔断是同一哲学的两个落点：**重试不能无限（轮次熔断）、扇出不能无限（实例上限）**。

## E4 协调问题实验：循环故障的注入 → 观察 → 修复对照（✅ 2026-11-04）

> 产出：step4_failure_lab.py——故障注入把概率故障变确定性故障，两组单一变量对照
> （共同：苛刻终审注入器；唯一变量：打回熔断），完整走通"现象 → 根因 → 机制修复 →
> 对照验证"。记忆钩子：**注入复现，对照归因；业务熔断，先于兜底。**

### 1. 协调问题为什么靠实验：概率故障的可见性

**成员间的配合失灵是概率行为——协调问题在代码里看不见，跑了才知道。** 成员靠
prompt 规则与路由信号配合，每个环节单看都对，连起来才出问题；要让故障可研究，
先让它确定性复现。

- **实验对象选循环**：step3 真实存在的熔断缺口——阶段C终审打回没有次数上限
  （MAX_ROUNDS 只熔断研究批次，不管打回次数），唯一防线是框架 recursion_limit；
- **故障注入**：在 LLM 决策产生后、写回 State 前，用代码强制改写决策（苛刻终审
  无条件打回）——概率故障（终审可能放过）变确定性故障（必然打回）；
- **注入与熔断同位反向**：同一个检查位置（`router.invoke` 之后、返回之前），熔断是
  "LLM 想继续时代码叫停"，注入是"LLM 想停时代码叫继续"——共同准绳即 E3 §5：
  决策产生后，代码做最后裁决；
- **单一变量对照**：两组共用注入器，唯一差异是熔断分支 3 行——故障组循环耗尽
  recursion_limit 抛 GraphRecursionError，修复组 2 次打回后代码强制 END、答案保留
  带保留意见收尾。对照让因果可归因：停止方式的差异完全由那一处代码决定。

### 2. 中间态注入：从任意 State 启动

**State 满足 schema 即可从任意中间态直接 invoke——等价于手工模拟 checkpoint 恢复。**

注入材料 1 份 + 偏题答案 + round_count=2，supervisor 第一步就落在终审，研究阶段
整个跳过。目标环节之前的全部流程都可以用一份构造的 State 替代——实验与调试的
杠杆：不用等 20 分钟真实研究跑完才够到要测的环节。

### 3. 双层防线：业务熔断先行，框架兜底最后

**带环系统有两层防线，业务熔断在内、框架兜底在外；兜底层被触发 = 业务熔断设计
有漏洞。**

- **业务熔断**：计数达上限后代码强制 END，业务层接管收尾——答案保留、附保留意见
  （用户拿到结果，且知道它的成色），即优雅降级；
- **框架兜底**：recursion_limit 按节点执行计步，耗尽抛 GraphRecursionError——用户
  拿到的是异常而非交付。修复成本极低（熔断 3 行），但不加，缺口就一直在；
- **try / except / else 把异常当作预期路径**：except 承接框架兜底并转成诊断输出
  （现象/根因/对照指引），else 承接正常收尾。语法：else 在 try 块无异常时执行，
  且其中的代码不被本层 except 捕获；finally 无论成败都执行（本实验未用）。

### 4. 观测：循环中的输入长度

**主图 State 是覆盖语义，不累积消息——循环中输入长度无系统性增长。** 实测一次性
过渡（注入的短答案重写回正常长度）后在区间内自然波动。真正的上下文膨胀发生在
ReAct 子图的消息历史（工具结果逐轮累积），对策是工具预算熔断（E2 已做）。

实跑同时印证 E3 §5 的准绳：prompt 写明"已打回次数 X/N"，终审 LLM 判定时会参考它
（软约束在工作、产生熔断意识），但改写权在代码——注入器无视 LLM 判定强制打回，
13 轮循环无一例外。

## E5 对照实验：这个任务什么时候单 agent 反而更好（✅ 2026-11-04）

> 产出：step5_single_vs_multi.py——同题公平对照（同一副工具、同一预算 10，
> 差异只在编排），结论有数据支撑。记忆钩子：**编排税买证据深度与纠偏，
> 三条件全中才付钱。**

### 1. 对照实验：控制一切变量，只留编排一个

**对照要公平**：单 agent 是一个 ReAct agent 把研究 + 综合合于一身（E2 researcher
子图 + E1 synthesizer prompt 的合体，预算熔断同样在）；多 agent 把 E3 系统
直接 import 上场，不重写。同一副工具、同一预算、同一道题，两侧差异只在编排。

实测的实质发现：**"单 agent"与"多 agent 里的一个成员"是同一种东西**——单 agent
的实跑行为（同预算、同熔断收尾、同决策节奏）就是 E2 researcher 的镜像。所谓
多 agent，是"一个成员"加上编排层（supervisor 决策环、工序分离、终审回环）。

### 2. 实测判读：编排税买到了什么

单 agent 71.3s 产出合格答案（结论先行、决策清单、局限说明俱全）；多 agent
493.5s（6.9 倍），换来的是单 agent 拿不到的东西：**一手数据**（多实例并行 +
补查定向补证据，如 GitHub API 硬指标）与**交叉验证纠偏**（实例互相看不见，
补查实例修正首轮材料的偏差描述）。

**编排税不是白交——supervisor 的每次结构化决策与工序分离买的是证据深度与
纠偏能力；任务不需要这两样时，它就是纯开销。**

### 3. 选型判据：三条件的反面补全

单 agent 更好的场景（满足任一即可）：

- **单一检索线**：拆维度无收益，一个循环顺序搜完即可；
- **资料一个上下文装得下**：切分丢全局视野，综合时反而见不到全貌；
- **决策环节没有内容价值**：拆题 / 判材料是形式判断时，supervisor 每次调用
  都是纯决策开销；
- **成本或延迟敏感**：编排税 = 多次 LLM 决策 + 串行环节叠加延迟。

多 agent 值得付税的场景（E2/E3 实证）：维度真可并行（提速 + 互不见的交叉
验证）；单上下文装不下全部材料（切分是必需而非选择）；验证需要独立视角
（synthesizer 只见材料不见搜索过程，机制上杜绝编造来源；终审是独立于产出的
二次判断）。

一句话总纲：**E1 三条件（可并行 / 上下文可切分 / 结果易验证）全中才上
multi-agent；不中的部分，每个编排环节都是税。**
