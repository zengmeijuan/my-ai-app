# C 评测笔记：迷你评测的设计思路

> 里程碑 C 沉淀。三个目标：评测意识（改前先证明方向对）/ 评测方式（建集→跑分→归因→观测→回归）/ 生产手段（离线·judge·门禁·坏例回流）。

## 1. 评测对象：一套可替换配置的完整系统

被测物 = LangGraph 图 + 工具 + prompt + 检索参数 + 模型，**组合体**才是被测对象——换其中任何一个，评测结论就要重新签发（门禁纪律的由来）。

| 被评层 | 评什么 | 承担者 |
|---|---|---|
| 结果层（端到端） | 最终答案对不对 | 25 条全量 |
| 行为层（轨迹） | 该调的工具调了吗/该禁的禁了吗 | expected_tools 字段 |
| 组件层 | 检索器本身的质量 | C5 专项（retrieval_cases） |

生产评测四级对象：单次 LLM 调用 → 组件 → 端到端 agent → 业务指标（解决率/满意度，需真实流量，迷你项目到不了但要知道）。

## 2. 评测集设计思路（testcases.json v1，25 条）

**定位：golden dataset（黄金评测集）**——人工标注真值的固定基准集，兼任回归基准（regression benchmark）与对比实验的对照组锚点。设计六原则：

1. **基准固化与版本管理（version pinning & immutability）**：测试集一经定版即冻结——改的是被测物，尺子不动，跨 run 可比性是评测的生命线；坏例回流走版本升级（v1→v2），旧基准归档不覆写
2. **分层设计（stratified design）**：样本按「能力维度 × 失败模式」双轴分层，不追求类别均衡——retrieval 15（主场景 + C5 组件级样本盘 + 子图对比实验盘）/ tool 3（行为合规）/ combo 3（多工具协作 + 跨文档推理）/ refusal 2 与 chitchat 2（负向能力：不编造、不越权干活）。**失败模式覆盖优先于类别配比**——agent 的失败一半发生在能力边界上
3. **对照设计（contrastive pairs / minimal pairs）**：最小对立对埋在易翻车处——R01 精确问法 vs R02 口语（查询改写的双向考验：别改坏好查询、别放弃差查询）；R07 裙子（可退）vs R08 内衣（不可退，近似商品的检索精度边界）；C01 复刻 step1 原版工单题作回归锚点（regression anchor）
4. **标注模式即测试预言（label schema as test oracle）**：字段定义即判定逻辑，评测器零猜测——
   - expected_points：只收字面可断言的硬信息（数字/政策短语），做信息点级断言而非全文相似度比对（判信息点不判措辞）
   - expected_tools：轨迹级 must-call 断言（该调的必须调、多调不罚）+ 禁调断言（空数组 = 不允许任何工具调用）——结果对且轨迹对才算真对，防「心算蒙对」的假阳性通过
   - notes：judge_required 标注 + 判定口径（如 X02：答支持=失败，如实告知未支持=通过）——LLM-as-judge 的 rubric 前置到数据侧，且必须显式传入 judge prompt 才闭合（C6 教训：只写不传，judge 看不见）
5. **真值独立性（ground-truth independence）**：要点逐条溯源知识库原文（ground-truth provenance），标注合法性与被测系统解耦——评测集自身有错会系统性冤枉 agent，正确率即毒数据；知识库无依据的（拒答类）要点留空，显式交 judge 裁定比硬凑字面要点诚实
6. **范围界定（scope control）**：显式声明 v1 边界——不做多轮对话（单轮基准，多轮评估挂后续版本）、不存标准答案全文（信息点断言已够，见原则 4）、不引外部评测框架（迷你规模自研判定链本身就是学习目标）

一句收束：**分层覆盖失败模式、对照对埋在边界、断言前置进数据、真值解耦防冤案**。

## 3. 评测执行器设计思路（eval.py）

本质：**可重复的控制变量实验机器**。三原则：隔离一切非确定性源 / 成本分层 / 失败隔离。

数据流：`main → load_graph(装配+补丁) → run_case ×N(重置记忆→invoke→采集→grade) → aggregate → print_report → 落盘`

| 设计点 | 实现 | 动机 |
|---|---|---|
| 温度固定 | setattr llm.temperature=0；step5 judge_llm 用 patch 后 llm 重建 | with_structured_output 在导入时固化旧参数 |
| 记忆污染防护 | MEMORY_PATH 重定向临时文件 + **每条前清零** | remember 写入会污染后续用例的 system prompt，跑两次结果不同 |
| 混合判定 | 关键词全命中→免费通过；未全命中或要点为空→judge 兜底 | judge 只做仲裁不做筛查，基线 25 条只花 6 次 judge |
| 失败隔离 | try/except 双形态 record（字段 schema 完全一致） | 异常也是合法记录计入分母——吞异常=美化正确率 |
| 结果自包含 | 汇总+元数据（图×测试集版本）+records 单 JSON，时间戳文件名 | 单文件=一次完整实验存档，历次 run 可 diff |
| 成本观 | 价目表查不到只报 token 不猜价格 | 内网模型套公开牌价 = 造假 |
| 报告可用性 | PASS/FAIL 纯 ASCII、失败原因优先级、判定来源标签（kw/judge） | Windows GBK 控制台中文会乱码；一眼看出为什么挂 |

judge prompt 两面都写显式：宽松面（允许措辞不同、信息更丰富）防误杀；严格面（关键事实不得缺失/答反/编造）防放水——judge 质量一半在边界声明。

## 4. eval.py 实战踩出的三个 Python 坑

- **from X import Y 是值拷贝**：patch 必须打在「名字被解析的那个模块」上——MEMORY_PATH 双 patch（remember 查 my_agent.agent 全局、build_system_prompt 查 step1_graph 全局，两刀都要切）。C 收官补精确化（单测 monkeypatch 实战引出）：**拷贝的从来只是「名字→对象」的绑定，对象从不复制**——Y 是子模块时（`from my_agent import rag`），模块对象全进程单例，test_eval 的 rag_mod 与 retrieval_eval 的 rag 是同一对象，setattr 改它的属性**全局可见**，写法 `rag.retrieve(...)`（运行时属性访问）必被 patch 波及；Y 是模块内名字时（`from my_agent.rag import retrieve`），裸名绑定在 import 时定死，patch 原模块够不着。判定 patch 影响某段代码的唯一标准：**那段代码怎么拿到目标**——属性访问（`x.y(...)`）受影响，裸名（`y(...)`）不受。实证：retrieval 单测 0.8s 全绿本身即 patch 生效之证（真检索要加载 161M embedding 模型且不可能给出 A.md 双现的剧本结果）
- **导入时固化的派生物要重建**：bind/with_structured_output 返回的新对象不受后续 setattr 影响；而 bind 链是 bound=self 共享属性，setattr 原对象能穿透
- **sys.path 与打包**：uv editable install 让包（my_agent）免 path；裸脚本（step1_graph）必须手动插 src/langGraph_agent

## 5. 首轮基线（run_20261023_105116，step1 图 × testcases v1）

正确率 **96%（24/25）**：retrieval 14/15 · tool 3/3 · combo 3/3 · refusal 2/2 · chitchat 2/2
延迟 avg 7.6s / p50 6.8s / p95 12.6s；token in 70.3k / out 11.0k；judge 6 次；异常 0。

**R13 的教训（本轮最大价值）**：首跑 FAIL——模型把过程汇报当成了给顾客的答复（"已按知识库口径答复并写入记忆…"，顾客啥也没得到）；单跑重测 PASS 且答案高质量。两个结论：
- deepseek-v4-flash 存在**偶发走神**，单次 96% ≠ 真实水平——方差纪律（关键结论跑 2~3 遍）的现场证明
- 判定链两种情形都对：坏回答 judge 判 FAIL，好回答关键词命中省 judge

## 6. C3 失败分类：四档归因 + 配置适配

判定语义：**分类是归因不是评分**——只对 FAIL 做，PASS 零成本（与 grade 同构的混合判定：规则先行、LLM 兜底）。

| 档 | 分类码 | 判据 | 成本 |
|---|---|---|---|
| 检索没命中 | retrieval_miss | 调了检索但返回资料撑不起答案 | LLM 三选一 |
| 工具选错 | tool_miss / tool_extra | 漏调（must 未满足）/ 误调（禁调却调） | 纯规则 |
| 编造引用 | fabrication | 答案与检索资料矛盾或无中生有政策 | LLM 三选一 |
| 其他 | other | 元回复泄漏、资料够但没用好、执行异常 | 兜底 |

三个落地要点：

- **采集决定归因上限**：新增 record.retrieved_context（每次 search_knowledge 的 ToolMessage 内容截断存档）——没有它，「检索没命中」和「资料在但模型没用好」分不开；历史 run 只能 `--reclassify` 降级重分类
- **preflight 配置适配**：expected_tools 含被测图未注册的工具 → SKIP 不计分母（配置性失败 ≠ agent 失败）。step5 的 80% 在此口径下修正为 20/21 ≈ 95.2%，与 step1 的 96% 才可比
- **历史数据回填坑**：--reclassify 时老 record 没有 expected_tools 字段（C3 才加），setdefault 空数组会把「漏调」误判成「误调」——从当前测试集按 id 回填，golden dataset 是判定语义的唯一权威

真实坏例归档（首批）：基线 R13 → other（元回复，LLM 归因精准指认「把过程汇报当答复」）；step5 Z02 → tool_extra（禁调却调 3 次检索）；step5 T01-T03/C02 → tool_miss（实为配置性，新口径下应 SKIP）。

## 7. C4 trace：LangSmith 接入与「树的深度 = 归因的层」

**接入**：零代码——.env 三行（LANGSMITH_TRACING / LANGSMITH_PROJECT / LANGSMITH_API_KEY；langsmith 0.14.8 随 langchain-core 自带）。eval.py 唯一改动：invoke 的 config 加 run_name=eval:<图>:<用例id> + metadata——trace 可按用例筛选，是「定位一次真实失败」的前提。服务端验证：client 查到 eval:step1:Z01，success。

**trace 树 = 失败定位的四层 SOP**（R02·step5 实测，25.2s）：root → agent（模型层：ChatOpenAI 输入 = system prompt + 历史，输出 = tool_calls 决策）→ tools（工具层：ToolNode）→ 子图内部（检索层：rewrite/retrieve/judge 全裸奔）→ 任意节点点开输入即 prompt 层。**树的深度就是归因的层**——这就是「说清失败发生在哪一层」的操作定义。

**token 盲区量化（step5「更省」结论正式翻案）**：R02 一条，eval.py 统计 in=1395/out=413（仅主图 2 轮 AIMessage）；trace 真实总账 in=2670/out=1487（根节点 rollup，与叶子精确对账）——盲区 in 48% / out 72%，全是子图 rewrite×2 + judge×2。自愈检索单次代价：输入近翻倍、输出三倍。**评测器看不见 ≠ 成本不存在**——C2 只看消息轨迹是管中窥豹，平台观测补全。

**并行实锤 + 意外发现**：tools 节点 17.5s 内含两条 search_knowledge（17.5s / 15.5s 时间重叠）——同一条 AIMessage 的多个 tool_call 被 ToolNode 并发执行（子图 print 交错是旁证）。且 agent 自己填参时已做查询改写（'钱多久能回来'→'退货退款流程 原路退回 到账时间'），子图 rewrite 对规范入参原样放行；agent 还并行发了两个近义查询对冲，多花一份检索钱。

**延迟大头是 judge**：11~13.1s（结构化输出带长 reason）vs rewrite 3~4.4s、retrieve ≈0。C5 若动 step5 延迟，第一刀在 judge。（另：rewrite 输出 token 296 远大于一条查询的合理体量——疑似网关模型夹带思考文本被 .strip() 吞掉，在 LangSmith 点开 rewrite 的 raw output 可验证。）

**Z02 方差第二课 + trace 必须常开**：23 号 FAIL（3 次检索、203s），26 号三连 PASS（0 次检索、~4.5s）——同图同温度同评测器。温度 0 穿网关 ≠ 确定性（服务端路由/负载/版本漂移）；23 号全轮延迟劣化（86~203s），疑似网关降级窗口——**评测环境本身也是变量**。间歇性失败无法事后 trace（23 号没录像）——**trace 常开是生产纪律**：出事再开 = 永远开不着。

## 8. C5 调优实验：句级切分对照（两级证据链全记录）

**组件级评测先于调优建成**：testcases.json 新增 retrieval_cases（15 条，expected_sources 标注应命中文件，与端到端用例同题）+ 独立执行器 retrieval_eval.py（直评 rag.retrieve，不经 LLM，纯函数零方差）。判定口径：期望来源 top-k 全覆盖 = HIT，另记 best_rank / best_score 留作对比基线。

**元教训（评测器自身也要被质询）**：首版基线显示「hit@3 100% 但平均名次 2.53」——满分辨识却整体垫底名次，是统计口径异常的组合信号。排查发现 got_rank 用字典推导实现，**同 key 后写覆盖先写**：期望来源占 top-3 多坑时记录的是最后名次而非注释声称的首次名次（15 条里 13 条占多坑，「rank3=11」纯属记录 bug 假象）。修复用 setdefault 保先。差点基于错误基线启动「总述段稀释」调优——基线数字被信任之前，先质询它合不合理。

**对照实验（段落级 v1 · 20 chunk → 句级 v2 · 51 chunk）**：v1 基线 hit@3 与 rank1 双满分（15/15），唯一数据靶子是 R12 0.38 / R06 0.42 低分，假设「关键句埋段尾被稀释」。句级（每句独立成块、重复携带小节标题前缀）结果：hit/rank1 完全不变，score 重分配 5 升 10 降（显著项如下，R13 +0.014、R10 +0.029 亦微升）——

- 兑现假设：R14 +0.21、R04 +0.06、R01 +0.05（关键句埋尾的查询独立成块后不再被段落稀释）
- 反向受损：R08 -0.11、R05 -0.10（主题词密集段的查询，整段语义平均反而更贴多成分查询）
- 假设证伪样本：R12 0.38→0.35 反降——「如忘记密码…」独立成块后只有 14 字向量太薄，而 v1 整段含「密码」主题词 5 次、语义密度更高。**R12 低分是查询与知识库表述的固有语义距离，chunk 粒度治不了**（rank1 始终正确，分数低 ≠ 检索错；那需要查询改写，即 step5 rewrite 的领地）

**端到端回归（trace 常开）**：25/25 = 100%（v1 基线 96%），retrieval 15/15 全部关键词直判，judge 仅 5 次，token 67.8k/10.9k（v1 70.3k/11.0k 略省——资料从整段变单句更精炼）。Z02 本轮 PASS（0 工具 3.63s，蹲守未复现）。**方差诚实声明**：100% vs 96% 的差异主要来自 R13（v1 基线偶发走神 FAIL，本轮 kw 直判 PASS），不能归功于句级切分。

**决策**：按预注册标准（端到端 ≥ 96% 保留）**句级切分留任**。v1 索引存档 data/rag_index_paragraph_v1.json。门禁纪律生效：被测物（chunking）已变更，v1 时代的 96% 签名作废，新签名 = run_20261027_162655 的 100%。

## 9. C6 收尾：坏例回流 v2 + 门禁纪律 + 生产评测手段一览

**坏例回流（testcases v1→v2，v1 归档 results/testcases_v1_archive.json）**：

- R04（话术缺陷回流）：「要点全中免 judge」的快速通道让「如需归档请您那边补录」类推诿话术漏网——v2 把 judge_required 从 notes 注记升级为 grade() 的执行语义（notes 含标注即强制 judge，要点全命中也不免检），R04 回流为首个受益用例。教训：**标注不接执行语义 = 装饰**——数据侧的 rubric 必须有判定器配合才闭合
- R13（元回复口径回流）：notes 补「把过程汇报当答复 = FAIL」静态判定口径，judge 的 rubric 继续前置到数据侧
- 单跑验证：R04 强制 judge 后 PASS（judge 来源标签）；重构后 step1/step5 主链路与 reclassify 离线归因三路复验全通

**口径断裂补修（C6.x，质疑驱动）**：R04 的判定口径写在 notes 里，但 judge_answer 的 prompt 只拼 question/points/answer——**rubric 从未送达判定者**，judge 拿通用标准自觉发挥（R04 强制 judge 那次的 judge_reason 全是「覆盖要点/未答反/未缺失」，无一句涉话术）。修复：judge_answer 加 rubric 参数（prompt 插「特别判定口径（必须严格执行，违反即不合格）」段），grade() 把 judge_required 用例的 notes 整段传入。验证三路：假 LLM 断言口径文字入 prompt；真 judge 对照（同一话术答案，旧路径靠自觉泛化判「内容不当」，新路径精确引用口径判 FAIL——判定依据从模型发挥变契约）；Z01（带口径走 judge）PASS + R01（免检通道）PASS 无回归。教训升级：**执行语义接了、rubric 没传 = 只看一眼，没戴眼镜**——「标注→执行语义→口径入 prompt」是三段链路，每段都要单独验证；这个断裂是靠质疑 judge_answer 函数签名发现的，验证员探针验的是「结论能传导」，没验「输入真送达」，两头都要验

**eval.py 小重构（C6 顺手）**：_GRADED_LLM 全局注入消除——load_graph 返回 (graph, tools, llm) 三元组，judge/归因 LLM 随被测图走，run_case / reclassify 显式收参。原实现硬编码 `from step1_graph import llm`，step5 模式下靠「恰好是同一对象」才工作，属隐性耦合；`from X import Y 是值拷贝`的坑（§4）这里又埋了一处，重构后自然消失

**门禁纪律（成文）**：被测物 = 图 + 工具 + prompt + 检索参数 + 模型（§1），任一变更 → 历史评测结论签名作废，必须重跑回归才可签发新结论。C5 已实践：chunking 变更 → 96% 签名作废 → 新签名 = run_20261027_162655 的 100%。门禁防的是「拿旧分数给新配置背书」——组合体变了，旧分数描述的不再是它

**生产评测手段一览（迷你项目到不了，但要知道）**：

- CI 门禁：PR 触发评测跑分，低于阈值拒绝合并——评测器从「实验工具」升级为「质量闸门」
- 线上采样 judge：生产流量抽样交 LLM-as-judge 评审，坏例回流进回归集（Z02 蹲守是它的手动雏形）
- A/B 与影子流量：新配置 shadow 跑同流量、不返给用户，离线对比后再放量

## 11. 收官自评后的两项加固（C 收官次日）

**评测器单测落地（evals/test_eval.py，23 用例，uv run pytest evals/ -q，0.8s 全绿）**：靶子取自两次自伤——got_rank 保先语义（同源多 chunk 取首次名次）、grade 判定矩阵（含「rubric 文字必须出现在 judge prompt」断言，把口径断裂锁成回归锚）、classify_failure 规则四向、percentile 边界、extract 系列轨迹采集。全部 FakeLLM/monkeypatch 零网络。**评测器是所有评测数字的裁判，裁判说谎没人知道——单测是裁判的裁判**。

**judge/归因 token 入账（judge_tokens_in/out，单列不混图内账）**：judge 与归因 LLM 调用在评测器侧发起，extract_tokens 扫图消息扫不到，cost_usd 一直低估。取数走 bind_tools 直取 AIMessage.usage_metadata（与 extract_tokens 同路径）。LangSmith 交叉对账：平台自采 judge trace（in=356/out=520）与评测器自采**逐位一致**，两个独立来源互相印证。

**调试过程的教训（比功能本身更值钱）**：token 丢失的假根因排查了两轮（callback handler 被 config 合并拷贝→contextvar 残留），都由实验证伪；真凶是 classify_failure 的 PASS 短路分支返回值里初始化了 judge_tokens=0，`record.update()` 把 grade 刚写对的值覆盖——**「update/覆盖语义吃掉已有数据」是本项目第三次踩坑**（got_rank 字典推导覆盖、rubric 写而不传、本次短路覆盖），单测里值得给「字段不被下游覆盖」专门留断言。另：调试时若某字段值异常，先查「谁最后写的它」，而不是假设「谁没写到」——SPY 看到回调正常就该先怀疑数据被覆盖，而不是虚构框架黑盒机制。
